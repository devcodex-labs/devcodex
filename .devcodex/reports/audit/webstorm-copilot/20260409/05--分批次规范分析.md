## 问题一：当前 Audit 规范中是否存在"分批次"相关规定？

### 逐文件检查

| 规范文件 | 是否包含"分批次"规则 | 相关内容摘要 |
|---------|:-----------------:|-------------|
| `12-audit.instructions.md` | ❌ **无** | 仅定义多轮收敛条件（连续 N 轮无新发现），未提及文件量阈值或批次策略 |
| `audit-common/SKILL.md` | ❌ **无** | G1~G5 公共维度层，所有子类型必先执行，未包含体量评估步骤 |
| `audit-execution-guide/SKILL.md` | ⚠️ **部分存在** | 包含"维度优先级分批"（按维度分阶段执行），但针对的是**维度层面**的执行顺序，非**文件量/响应量**层面的批次控制 |

### 关键区分：两类"分批"概念

当前规范中存在两类不同的"分批"概念，容易混淆：

| 概念 | 当前状态 | 触发条件 | 控制层面 |
|------|---------|---------|---------|
| **维度分批**（Dimension-based） | ✅ `audit-execution-guide` 已定义 | 按维度优先级分阶段执行（D1优先于D21等） | 审查维度层面 |
| **体量分批**（Volume-based） | ❌ 无规范 | 项目文件总数超过平台响应长度限制时 | 文件数量/响应量层面 |

**结论**：体量驱动的分批次规范（Volume-based batching）在现有三个核心规范文件中**均不存在**，仅以项目级 profile 备注形式记录于 devcodex。

## 问题二：将"分批次"提升为通用规范的合理性分析

### 问题根源

此问题本质是一个**平台级技术约束**与**规范缺口**的叠加：

1. **平台响应长度限制**：AI Agent 单次回复有长度上限，大型项目（如 devcodex 有 67 个规范文件）在全面 audit 时必然触发该限制
2. **规范缺口**：现有 audit 规范未规定"文件量超限时如何处置"，导致各项目自行发现、自行记录
3. **重复发现成本**：每个大型项目在第一次全面 audit 时都会独立踩到这个坑，这是可以用规范预防的知识损耗

### 问题的普遍性评估

| 项目类型 | 预计审查文件数 | 触发风险 | 典型项目 |
|---------|:----------:|:------:|---------|
| 小型模块（单一功能库） | ~5~15 | 🟢 低 | flex-rate-limit, monSQLize |
| 中型项目 | ~20~40 | 🟡 中 | cache-hub, vext, schema-dsl |
| 大型项目（含规范文件） | 60+ | 🔴 高 | devcodex |
| 全工程 audit（跨模块） | 100+ | 🔴 极高 | MySelf 全工程 |

**置信度**：🟢 高（基于工作区实际项目分布推断）

随着项目规模增长，文件量触发限制不是偶发事件，而是**可预期的结构性问题**。

### 三项验证

#### ✅ 合理性

- 平台响应长度限制是客观存在的技术约束，不受单一项目控制
- "维度分批"规范已证明 `audit-execution-guide` 承载此类策略的可行性
- 其他工程领域（如 CI/CD 分阶段流水线、测试分批执行）均有"批次策略"的通用规范化先例
- 将偶发 profile 备注升级为通用规范，符合"知识从项目级提炼为平台级"的规范演进路径

**置信度**：🟢 高

#### ✅ 可实施性

落地方式明确，不涉及框架性重构：

1. 在 `audit-execution-guide/SKILL.md` 增加"体量评估"前置步骤（E0）
2. 定义文件量阈值（建议：`> 30 文件` 触发分批提示，`> 60 文件` 强制分批）
3. 提供标准分批策略：按维度优先级分轮（P0维度 → P1维度 → P2维度）
4. 在 `audit-common/SKILL.md` 的入口步骤增加体量检测条目（G0）

**前置条件**：需要通过 self-fix 或 dev 工作流将新规则写入对应 SKILL.md

**置信度**：🟢 高

#### ✅ 收益

| 收益维度 | 具体改善 |
|---------|---------|
| **质量一致性** | 所有项目 audit 开始前执行体量评估，避免首次 audit 失败 |
| **效率** | 消除各项目重复踩坑的学习成本 |
| **用户体验** | Agent 主动提示分批策略，而非用户事后发现响应截断 |
| **规范完整性** | 补全"维度分批"与"体量分批"之间的规范空白 |
| **知识沉淀** | 项目级经验提炼为平台级通用规范 |

## 问题三：应该放在哪个规范文件？

### 候选位置评估

| 位置 | 优点 | 缺点 | 推荐度 |
|------|------|------|:-----:|
| `audit-execution-guide/SKILL.md` | 已有"维度优先级分批"，主题高度一致；是执行策略文件 | 需补充"体量评估"这一新前置维度 | ⭐⭐⭐ **首选** |
| `audit-common/SKILL.md` | 所有子类型必先执行，适合前置检查 | 主要职责是公共维度定义，混入执行策略略超职责边界 | ⭐⭐ **配合角色** |
| 新建 `audit-capacity.md` | 职责纯粹，扩展性好 | 新增文件增加规范体系复杂度，当前内容体量不足以撑起独立文件 | ⭐ 暂不推荐 |
| `12-audit.instructions.md` | 顶层 Instructions 覆盖范围广 | 已过于精简（核心约束层），加入执行策略会稀释层级语义 | ⭐ 不推荐 |

### 推荐方案：双文件协作

**层次分工**：

```
audit-common/SKILL.md（前置检查层 — 决策："要不要分批"）
└─ 新增 G0: 体量评估（在 G1~G5 之前执行）
   - 统计待审查文件/目录总数
   - 1~30 文件：直接执行全量 audit
   - 31~60 文件：建议定向审查（输出分批建议，等待用户确认）
   - > 60 文件：强制分批（输出分批计划后自动开始第一批）

audit-execution-guide/SKILL.md（执行策略层 — 指导："怎么分批"）
└─ 新增"体量分批策略"章节
   - 分批原则：优先级驱动（P0维度 → P1维度 → P2维度）
   - 单批次建议：每批覆盖 ≤ 3 个主维度
   - 批次间记忆：将上批结论通过 memory/SKILL.md 写入 .devcodex/.memory/
   - 特殊场景：audit-project（代码质量）维度建议独立成批
```

**方案优势**：
1. **层次清晰**：`audit-common` 做决策，`audit-execution-guide` 做执行
2. **最小改动**：无需新建文件，与现有体系结构一致
3. **可扩展性**：阈值和分批策略可在 `audit-execution-guide` 中独立演进
4. **与维度分批无冲突**：体量分批是在维度分批策略基础上的外层包装
