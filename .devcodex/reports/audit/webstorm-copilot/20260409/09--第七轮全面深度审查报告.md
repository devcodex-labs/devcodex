## 问题 1：RULES.md vs copilot-instructions.md 角色分析

### GitHub Copilot 文件体系（官方约定）

| 文件/目录 | 加载方式 | 说明 |
|-----------|---------|------|
| `.github/copilot-instructions.md` | ✅ **平台自动加载** | 全局指令文件，每次对话自动注入 |
| `.github/agents/*.agent.md` | ✅ **用户触发加载** | `@AgentName` 时加载对应 Agent 文件 |
| `.github/instructions/*.instructions.md` | ✅ **平台按 applyTo 自动加载** | 上下文匹配时自动注入 |
| `.github/prompts/*.prompt.md` | ✅ **用户手动触发** | Slash 命令或引用时加载 |
| `.github/skills/*/SKILL.md` | ⚠️ **Agent 内引用读取** | Agent 运行时按需 read_file 读取 |
| `.github/RULES.md` | ❌ **不会自动加载** | 非 Copilot 标准文件，平台不识别 |

### RULES.md 在 DevCodex 中的角色

**结论**：`RULES.md` 在当前架构下是 **功能冗余但有文档价值** 的文件。

| 维度 | 分析 |
|------|------|
| **来源** | 继承自 `ai-dev-guidelines` v4 框架的入口文件概念 |
| **平台功能** | ❌ Copilot 不会自动读取 `.github/RULES.md`，它不是平台约定文件 |
| **内容冗余** | 其内容（意图路由表、安全底线摘要）已完整覆盖在 `01-common.instructions.md` + `00-safety.instructions.md`（这两个文件 `applyTo: "**"` 会被自动注入） |
| **实际作用** | 纯人类可读的"快速导览"文件，类似 `.github/` 目录下的 README |
| **CLI 行为** | `npx devcodex init` 会将其复制到 `.github/RULES.md`（69 个文件中的第 69 个） |

### 是否应该改名为 copilot-instructions.md？

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|:----:|
| 保留 `RULES.md`（现状） | 与 ai-dev-guidelines v4 一致；不影响功能（instructions 已覆盖）| Copilot 不读取，纯文档价值 | ✅ 可接受 |
| 改为 `copilot-instructions.md` | 被 Copilot 自动加载 | 与 11 个 `instructions/*.instructions.md` 内容重复，可能造成上下文浪费 | ❌ 不推荐 |
| 删除 `RULES.md`，仅保留 instructions | 最精简 | 失去人类可读的快速入口 | ⚠️ 可选 |

**最终建议**：**保留 `RULES.md` 但明确定位为人类可读导览**。DevCodex 的核心机制是 11 个 `instructions/*.instructions.md`（`applyTo: "**"` 自动注入），不依赖 `RULES.md`。无需改名为 `copilot-instructions.md`。

**验证状态**: ✅已验证（通过 GitHub Copilot Agent Plugin 文档 + 实际 `applyTo` 机制确认）

### 🔴 P-01 `index.js` shebang 行被破坏 — CLI 无法运行（已修复 ✅）

| 验证 | 结论 |
|------|------|
| 合理性 | `index.js` 第 1 行为 `o#!/usr/bin/env node`，多了一个前置 `o` 字符。这导致：① Unix/macOS 系统 shebang 失效，`npx devcodex` 无法运行；② Node.js 解析时第一行报语法错误 |
| 根因 | 前次编辑（N-03 修复 "VS Code" 硬编码时）IDE 输入法残留字符污染了 shebang 行 |
| 可实施性 | 删除 `o` 字符，恢复为 `#!/usr/bin/env node` |
| 收益 | CLI 恢复正常运行 |

**验证状态**: ✅已修复并验证
- 修复后 `node index.js status` 正常输出
- 修复后 `node index.js init --dry-run` 正常列出 69 个文件
- `get_errors` 返回零错误

**修复详情**：
| 文件 | 修复内容 |
|------|---------|
| `index.js` 第 1 行 | `o#!/usr/bin/env node` → `#!/usr/bin/env node` |
| `index.js` cmdStatus | 移除未使用的 `argv` 参数 |

### 🟡 P-02 Token 预算风险 — 11 个 Instructions 全部 `applyTo: "**"` 同时注入

| 验证 | 结论 |
|------|------|
| 合理性 | 所有 11 个 `instructions/*.instructions.md` 均使用 `applyTo: "**"`，意味着 **每次对话都会注入全部 11 个文件的内容**。按实际行数统计：00-safety(52) + 01-common(192) + 02-output(98) + 10-dev(163) + 11-fix(116) + 12-audit(108) + 13-analyze(57) + 14-self-fix(67) + 15-memory(120) + 16-report(86) + 17-compliance(154) = **~1213 行** 规范内容注入每次对话 |
| 风险 | 消耗大量上下文窗口（约 25~35K tokens），压缩留给用户代码和 AI 推理的空间 |
| 可实施性 | 可考虑将工作流专属 Instructions（10~17）的 `applyTo` 改为更精准的路径模式，仅在相关上下文中触发 |
| 收益 | 降低 Token 消耗，提升 AI 对用户实际代码的关注度 |

**验证状态**: ✅已验证（逐文件统计行数确认）

**反向质疑三问**：
1. 不修复会导致什么具体功能异常？→ 不是功能异常，而是 Token 效率问题。但对小文件/简单问题会话影响有限
2. 是否有意的设计选择？→ **是**。DevCodex 设计目标是"所有规则全程有效"，`applyTo: "**"` 是有意为之
3. 不修复的风险是否可接受？→ **可接受**，但值得在 v1.1 版本评估按需注入方案

**影响文件**: 所有 11 个 `instructions/*.instructions.md`
**建议**: v1.1 评估。当前保持现状。

**验证状态**: ✅已验证（`plugin.json` 第 2 行已有 disclaimer）
**影响文件**: `plugin.json`
**建议**: 低优先级，`_format` 字段已覆盖此点

## Agent 模拟执行（Task 5）

### 模拟场景：用户在目标项目中输入 `@DevCodex 帮我重构 user 模块的权限校验逻辑`

#### 阶段 1：平台级自动注入

```
Copilot 平台自动执行：
├─ 加载 .github/agents/devcodex.agent.md（因用户 @DevCodex 触发）
├─ 注入 11 个 instructions/*.instructions.md（全部 applyTo: "**"）
│   ├─ 00-safety（S01~S06 安全底线）
│   ├─ 01-common（C01~C15 约束 + 意图路由表 + Skill 按需读取表）
│   ├─ 02-output-paths（产物路径规范）
│   ├─ 10-dev ~ 17-compliance（各工作流规则）
│   └─ 总计 ~1213 行规范内容已在上下文中
└─ 用户消息传入 AI

此时 AI 上下文中已有：
- Agent 定义（32 行）
- 11 个 Instructions（~1213 行）
- 用户消息
⚠️ RULES.md 不会被自动加载
⚠️ Skills 不会被自动加载
```

#### 阶段 2：AI 执行意图识别（01-common §意图识别）

```
前置识别：
  ├─ 恢复中断？→ 否（非"继续"/"恢复"）
  └─ 纯问答？→ 否（有文件变更意图）

三问判断：
  Q1: 最终目的是变更还是结论？→ 变更（重构代码）
  Q2: 分析是手段还是目的？→ 手段（为了执行重构）
  Q3: 是否需要修改/创建/删除文件？→ 是

结论：任一指向变更 → dev 或 fix
  └─ "重构" → dev.refactor 子类型
```

#### 阶段 3：Profile 加载

```
确定项目 → 用户消息涉及 "user 模块" → 映射到项目
读取 .devcodex/profile/README.md → 获取技术栈/架构约束/代码风格
读取 .devcodex/profile/config.json → 确定 ENV_MODE（dev/prod）
```

#### 阶段 4：按需读取 Skills（01-common §Skill 按需读取表）

```
dev.refactor 对应 Skills：
  ├─ read_file: skills/dev-refactor/SKILL.md（重构专属规则）
  ├─ read_file: skills/cp-gate/SKILL.md（CP 门控详细规则）
  └─ read_file: skills/dev-plan-review/SKILL.md（plan-review 质量门禁）
```

#### 阶段 5：C12 合理性评估

```
AI 评估用户请求合理性：
  ├─ 有更好方案？→ 评估后决定是否提出建议
  └─ 合理 → 进入 CP1
```

#### 阶段 6：CP 门控执行

```
CP1（需求确认）→ 输出 AI 对"重构权限校验逻辑"的理解
  ├─ 创建 .devcodex/requirements/<描述>/01-需求概述.md
  └─ 等待用户确认 ✅

CP2（方案确认）→ 输出重构技术方案
  ├─ 创建 02-技术方案.md
  ├─ 前置检查：被重构模块必须有测试覆盖（dev-refactor 规则）
  └─ 等待用户确认 ✅

plan-review（PR-1~PR-6 质量门禁）→ CP2→CP3 间强制
  ├─ PR-1 需求完整性 ✅
  ├─ PR-2 技术可行性 ✅
  ├─ PR-3 约束合规性 ✅
  ├─ PR-6 架构质量（C15 三维评估）✅
  └─ PR-5 标记：无 API 变更/无跨模块依赖 → 不触发 impact-review

CP3（实施计划确认）→ 输出逐文件执行计划
  ├─ 创建 03-实施方案/ + 04-实施计划.md
  └─ 等待用户确认 ✅
```

#### 阶段 7：执行

```
逐文件重构 → lint/typecheck/test
  ├─ error 最多 2 次迭代
  ├─ 每文件保持行为不变原则（refactor 规则）
  └─ 修复三步必做（同类扫描 + 数据联动 + grep 零残留）
```

#### 阶段 8：合规检查（17-compliance → compliance/SKILL.md）

```
prod 模式全量检查：
FC: FC1 ✅ FC2 ✅ FC3 ✅ FC4 ✅ FC5 ✅ FC6 ✅
SC: SC2 ✅ SC4 ✅ SC6 ✅ SC13 ✅ ...
RC: RC1 ✅ RC2 ✅
T: T1~T9 ✅

输出合规状态块 → 写记忆 → 写报告 → 输出产物路径
```
