# v1.16.7

> 发布日期：2026-08-11
> 类型：Patch

## 摘要

本版本修复 Grok 宿主可看到 MCP/Skill 目录却未可靠加载正文的问题：未提交的渐进式路由现在会在首次工具调用前阻止无关工作，同时保留 ContextRead 的合法完成路径；Grok Full 启动器固定实际可调用的限定 MCP 名与路由 schema，并用真实 entry/execution/closeout 证据晋级 capability PASS。

## 主要修复

- 非显式 `PLAN_NOT_COMMITTED` 仅在 PreToolUse 阶段强制；无工具的 Stop 不进入路由恢复循环，显式 Skill 请求仍在全部生命周期阶段 fail closed。
- 预提交路由只允许 `profile_load`、`memory_status`、`memory_session_query` 与 `memory_summary_query` 等精确只读工具通过，且 `ContextReadBindingV1` 必须匹配当前 project 与 context epoch；缺 binding、跨项目、跨 epoch 和无关工具均被拒绝。
- 首个 catalog 恢复调用不再携带 `cursor:null`；只有上一页返回非空 `nextCursor` 时才发送 cursor。
- `devcodex grok` 启动器与 Grok bootstrap 固定 `devcodex-profile__profile_context_plan`、`devcodex-profile__profile_load`、`devcodex-profile__skill_route`、`devcodex-memory__memory_status` 四个 server-qualified 名称，禁止误用未限定名或其他宿主别名。
- 条件阶段通过携带 `previousPlanDigest`、`lateConditionId` 与 fresh binding 的第二次 `commit` 激活；提示与 S15 不再调用不存在的 `replan` 操作。
- Grok S15 不再要求 npm 安装目录含 Git checkout；production probe 可直接从真实 tarball/registry 包验证 runtime 与 adapter identity。
- Host capability 证据增加 Grok 1.0.0 PASS，完整校验 runtime digest、launcher digest、package-relative evidence、entry/execution/closeout stages、local-stdio transport 与六项 retirement anomalies。

## 用户排障

- Grok Full 入口为目标项目目录中的 `devcodex grok`；普通 `grok` 是 Partial 兼容入口，不能用其被动 UserPromptSubmit 行为证明 Full 启动注入等价。
- `SkillRouteCommitReceiptV1` 只证明已完成路由决策；正文加载的权威成功回执是 `StageLoadReceiptV1`，项目中不存在 `SkillLoadSuccessV1`。
- 更新后执行 `devcodex global-adapters apply`，完全关闭旧任务并通过 `devcodex grok` 新建会话，才能加载新的用户级 runtime 与 launcher 规则。
- 该问题不是“必须开启完全访问权限”；权限与路由契约是两条独立诊断轴。
