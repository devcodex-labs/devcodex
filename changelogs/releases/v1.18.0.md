# DevCodex v1.18.0

> 发布日期：2026-08-23
> 类型：Minor / 跨宿主 AI Coding 工程 Harness、按任务恢复的有界 Hook 状态与交付治理

## 发布摘要

v1.18.0 将 DevCodex 明确定位为“跨宿主 AI Coding 工程 Harness”：它不提升模型参数、权重、上下文窗口或基础推理上限，而是通过上下文装配、Skill 路由、工程工作流、工具、记忆、验证和证据链，提高模型在真实软件工程中的有效智能表现，让 AI Coding 从“聪明地回答问题”升级为“聪明地完成工程任务”。

本版本同时修复 Codex progressive SkillRoute 在 `PreToolUse` / `Stop` 上可能形成的循环：渐进路由约束改为 feature-scoped advisory，危险命令、Context、CP、closure 等共享 Hook 守门仍按原事件链执行；Stop 重入、跨代运行时与失败终态统一进入可证明的有限状态机。

发布前深审还确认旧 lifecycle writer 几乎在每次 Hook/工具状态变化时创建 UUID 命名的完整 JSON；pointer 只限制可达引用，物理孤儿没有被回收，导致 `.devcodex/**/.memory/hooks/generations` 可在一周内增长到数十 GiB。本候选因此冻结发布链，并以 TaskRecoveryStoreV5 替换新 writer；随后又把用户级安装 `runtime-*` 的长期收敛 P2 纳入同版。用户已授权 P2、深审与 R4 全绿后直接发布，但旧资格证据不得复用。

## Codex Hook 循环与代际终止修复（PF-328）

- Codex 的 progressive route 在 `PreToolUse` 与 `Stop` 上不再通过硬阻断强制续写；该调整只作用于渐进 Skill 路由，不关闭同一事件上的通用安全、上下文、阶段与闭环检查。
- `stop_hook_active` 重入立即 observation-only；首次 Stop 仍执行非 progressive 的普通守门，避免续写回调再次进入同一路由。
- 当前/N-1 producer identity、terminal tool failure、三次无进展退休与旧 fingerprint 抑制形成同一有界闭环；损坏 tuple、未知 disposition、非法 digest 和非有限计数均失败关闭。
- policy 缺失或损坏时，Codex 两事件保持 advisory-safe，其余宿主与事件恢复 hard default，避免单个策略文件失效扩散到六宿主。
- 旧全局运行时升级时先安装新 generation、刷新 adapter，再恢复 Codex 五事件；旧任务继续使用启动时 generation，新任务或重启宿主读取新版本。

## TaskRecoveryStoreV5：按任务恢复，不按事件生成文件（PI-275 / PF-337）

- 正式任务以 `(activeRoot, project, taskId)` 的稳定 recovery key 保存，只使用 hot `state-a.json` / `state-b.json`；具备安全 checkpoint 后可降为不超过 16 KiB 的 cold resume stub，terminal 状态退出 hot cache。ordinary read-only Hook 的 full-state write 为 0，不再按 Hook/工具状态变化创建 UUID generation。
- 正式任务数量没有硬上限；容量按字节保护：hot 单槽/双槽上限 256/512 KiB，store 默认 soft/hard 为 256/512 MiB。达到 soft 时只安全冷化和退出过期缓存；达到 hard 时普通 mutation 在动作前失败关闭，不会静默删除活跃任务。
- 两个预分配 closeout 槽合计 8 MiB，并以 `TRV5RS01` 尾标证明物理准备；hard pressure 下仍可写最小收口。A/B inactive slot 的 open/write/fsync/rename/readback 失败都保留上一有效 checkpoint，锁创建失败关闭 descriptor 并清理本 writer 的精确锁。
- ephemeral entry/总量固定为 8 KiB/1 MiB、TTL 24 小时；telemetry 为 4×1 MiB ring，SkillRoute trace 不超过 256 KiB，ContextSource V4 为固定 128 槽。支撑 writer 的 temp/backup/stale/quarantine 也改为固定槽，避免从其他目录形成新的无界失败残留。
- Grok Plugin 先前每次 SessionStart 都创建随机 private owner 且没有 SessionEnd 回收；现改为 `GrokSessionPrivateObservationV2` 固定 16 槽诊断 ring。100 次会话压力后 JSON 不超过 16，故障注入不留 lock/temp/backup；它不限制正式任务，也不参与恢复或授权。
- `devcodex runtime status|doctor|maintenance` 同时报告 V5、legacy、物理磁盘、reserve、hot/cold/terminal/ephemeral 与 top task。maintenance 默认 dry-run；即使 `--apply` 也不删除旧 generation/temp/log。本版本对已有 legacy 文件零删除、零迁移、零覆盖。
- Profile 可设置 `extensions.devcodex.taskRecovery.hardLimitMiB`，只接受 safe integer `>=512`；workspace base + project overlay 生效。非法配置 fail closed 到 512 MiB 安全默认，并由 doctor 报 typed issue。

## RuntimeGenerationRetention：收敛用户级安装代次（PI-276 / PF-338）

- 用户 HOME 下各宿主的不可变 `devcodex/runtime-*` 与项目内 legacy lifecycle JSON 明确分层；后者继续零删除，前者新增可审计的长期收敛路径。
- Profile/Memory 长驻 MCP 按 `(generationId, role, pid)` 维护稳定 `RuntimeGenerationLeaseV1`：默认 30 秒心跳、120 秒 TTL，stdin EOF/正常退出主动清理；异常终止由 TTL + PID 探针保守判定。过期 lease 遇到仍可见 PID 而缺进程启动身份时保持 unknown，不冒险删除。
- `RuntimeGenerationGcPlanV1` 只选择非 current、无 live lease、已过本机 `generationAdoptions` 记录的 24 小时宽限，且 receipt、immutable manifest、候选内容树、ownership、权限和路径边界都可证明的 generation。旧 release 刚在本机采用不会因上游发布日期过早进入候选；同一 lease 的 heartbeat 不使摘要漂移，新 lease/回执/入口/内容变化仍会使旧计划失效。
- 普通 `runtime maintenance --apply` 不删除安装 generation；用户必须再次提交预览返回的完整 `--generation-plan <sha256>`。执行先建立独占 GC claim；global-host activation 也持有临时 lease，双方双向互斥。完整 claim replan 与全部候选预检失败时零删除，删除阶段逐项复核并如实返回 partial；崩溃遗留 claim 仅在超龄、PID 明确死亡且固定 stale 槽读回一致时恢复，reparse、权限或未知条目全部失败关闭。
- 不设置“只留 N 个”的数量淘汰，不引入 daemon 或外部依赖。同一内容 generation 重复 apply 幂等；`status/doctor` 在六宿主合计只投影 12 条 generation 样本，并把 root-level legacy temp 聚合为单类、每个 inventory 最多 12 类、TaskRecovery task 最多 8 条；maintenance 的 task before/after 各最多 8 条，actions/failures 与 generation candidates/retained/removed/failed 各最多 24 条。每个 runtime root 的 current refs 最多显示 12 条，每个 receipt 只保留 ref 总数。所有输出都保留真实总数/字节与 truncated，内部摘要仍绑定完整集合，避免状态查询本身制造数十万字符与不必要 Token 消耗。

## ContextDeliveryLedgerV2 与 Token 口径

- 只有 formal task、conversation、context epoch、project/root、source identity/digest、body digest/bytes 全部精确一致，且 PostToolUse 已观察正文时，Profile/SkillRoute 才返回小型复用描述；descriptor-only 或任一身份漂移都恢复全文。
- actual-shaped benchmark 的正文为 402,848 bytes；首次 serialized response 为 404,290 bytes，三次精确重复各为 1,846 bytes。每次重复避免 100% body bytes，serialized reduction 为 99.543%，约 80,570～134,283 UTF-8 token-equivalent。
- 该区间按 3～5 UTF-8 bytes/token 估算，不是宿主实际 tokenizer 或账单数据；宿主未提供 actual token 计数时状态保持 `UNVERIFIED`。停止或删除磁盘 generation 本身通常只带来约 0～<1% 的间接 Token 变化，不能冒充上下文节省。

## 跨宿主 AI Coding 工程 Harness

- README、公开站、package、plugin 与 CLI 统一使用 `PublicProductExpressionV2`，面向 Codex、Claude Code、GitHub Copilot、Gemini CLI、Grok 与 Cursor 六宿主表达同一产品身份。
- 明确 DevCodex owns：上下文、Skill、工作流、记忆、验证、证据和宿主适配；host owns：模型能力、原生 UI、权限、沙箱、事件投递和宿主级会话生命周期。
- 保留 “workflow runtime / host adapter” 作为技术架构术语；“Harness” 是用户与生态定位，不制造第二套运行时或常驻服务。

## 完成态动作、Git 与 worktree 透明化

- 新增 `PostCompletionActionSetV1` 与 `DevCodexVisibleEnvelopeV2`：完成态必须 `requiredNow=[]`，交付文件与下一步动作分离；接口文档、`.http`、commit、switch、cherry-pick、push 只在存在真实差额时提示。
- 默认继续在当前分支工作，不自动创建功能分支；同分支无需集成，跨分支选择性交付默认使用记录好的 commit ID 做 ordered cherry-pick。
- cherry-pick 仍可能冲突且会在目标分支生成新的 commit ID；Git 写动作逐项绑定显式授权，不把建议文本当作执行授权。
- `status` / `doctor` 提供有总预算的只读 `WorktreeDiagnosticsV1`；不自动清理 prunable/external worktree，不修改全局 `safe.directory`，也不把外部记录伪装成 DevCodex 创建来源。

## 开源安装后的本地进化

- 新增 `EvolutionTargetDecisionV1` 与 `.devcodex/workspace/evolution/{candidates,decisions,evidence}`，安装实例默认把进化候选留在 workspace 层。
- candidate 不进入活动 resolver；workspace Skill 晋级需要独立批准与证据，项目专属目标要求项目证据，修改上游 package 必须有维护者显式授权。
- 初始化与 dry-run 返回 fresh/existing/planned/failed typed receipt；dry-run 只规划、零写入，失败摘要与逐路径错误码保持一致。

## 验证路由与包闭包

- Git、Evolution、Workspace Provisioning、Worktree Lifecycle 同时声明 canonical `content/...` 真相源和 package 投影输入，changed-route 会对每个 canonical input 单独选择验证节点。
- 新增的 worktree/evolution/Git/provisioning 脚本、schema、fixture 与直接依赖进入 npm package 闭包，避免“源码可用、安装包缺模块”。
- `PostCompletionActionSetV1`、Visible V2、Harness 表达、版本消费者、Profile、公开文档与六宿主投影由定向测试、完整 V3、pack/install 和宿主回放共同验证。
- 隔离 exact-tree qualification 现在把 runner 已解析的 active-root 注入每个验证叶节点；V99 standalone 优先消费显式 `DEVCODEX_VALIDATION_ACTIVE_ROOT`，再回退 canonical resolver。这样 clean candidate、源工作树与 Profile 身份可以分栏取证，不再因资格仓物理位置误报 Profile consumers 缺失。
- immutable runtime generation 在候选阶段从 `候选日期` 派生确定性 `createdAt` 并记录 `creationTimeAuthority=candidate-changelog`；最终发行源码改用 `发布日期` 后投影 `release-changelog`。两种状态都保持确定性，且候选资格验证不会伪造已发布事实。
- TaskRecoveryStoreV5 与 RuntimeGenerationRetention 源码冻结后的 Codex CLI S15 已在 runtime `3c762817…daf842`、adapter `b4662345…d2f00` 上完成 Profile/Memory/SkillRoute、context rebind 与 entry/closeout 回放；run=`s15-codex-probe-f9b1014d-bde6-4381-8584-b23ce1e2af8d`，portable evidence=`55be4e4a…82524`，retirement anomalies 全 0。该 CLI 证据不替代 Codex Desktop fresh-task 原生事件验证。
- TaskRecovery recovery key 的路径大小写回归按宿主文件系统语义分栏：Windows 断言大小写变体 identity 相等，POSIX 断言不相等；Node 18.17/20.20/22.23/24.17/26.0 均通过 10,000 semantic no-op 与 1,000 formal-task 压测，避免 Windows 专属合同阻断 Linux CI。

## 兼容性、升级与边界

- 本版本不新增 root runtime dependency、后台服务、网络监听、registry 或自定义域名。
- 现有 workspace 数据不自动迁移到上游 Skill；新 evolution 目录按需初始化，候选默认不影响当前解析结果。
- 现有项目内 lifecycle generation/temp/log 不自动删除。升级只让新任务使用 V5 writer；安装后须完全退出旧宿主并新建任务，`runtime doctor` 若仍观察到 legacy 最近写入会返回 `LEGACY_WRITER_RESTART_REQUIRED`。用户级旧安装 runtime 只在显式摘要绑定的 generation maintenance 中处理。
- Cursor Local 继续为 Beta；Cursor Cloud Agent 不加载用户级 Hooks，保持 Partial / `UNVERIFIED`。Codex CLI 与 Desktop 证据继续分开，CLI 结果不能替代 Desktop 当前任务的原生事件证据。
- `.playwright-cli/` 继续从 Git 与 package 路径集合排除；发布验证不得读取、枚举、修改、移动或删除其内容。
- 升级后必须重启或新建 AI Coding 任务，并执行 `devcodex status` / `devcodex doctor` 核对宿主适配，再执行 `devcodex runtime doctor --json` 核对 V5 writer、reserve 与 legacy 最近写入。

## 失败恢复

- tag 或 registry 版本已存在时不覆盖，改用新的 SemVer 版本。
- publish 前失败可在修复并重新冻结候选后重跑资格链；registry 已接收版本而后验失败时只能发布新 patch 修复。
- exact tarball 摘要、远端 CI/Publish run、全局安装与 Codex Desktop 原生回放证据保存在包外发布报告和 attestation 中，避免 tarball 自引用。
