## PI-008
- 发现时间：2026-05-25
- 场景：开发/修复完成后，用户并未明确要求 `tag`、`release`、`publish`
- 原做法：变更日志、版本号、tag、publish 的边界定义不够清晰，实施层容易把“开发完成”顺滑推进成“准备正式发版”
- 更优做法：默认只记录 `changelogs/unreleased.md`；仅在用户明确确认 `tag` / `release` / `publish` 时，才固化版本号、归档正式 changelog 并执行 tag/publish
- 改进收益：避免预占未来版本号，减少日常开发误触发 release 流程，也让需求日志、未发布实现日志、已发布版本日志职责更清晰
- 状态：已纳入规范（发布与 CHANGELOG 双阶段模型）

## PI-009
- 发现时间：2026-05-25
- 场景：修复/开发过程中，一个会话内连续解决多个问题或多个同源发现项时，如何处理 `commit` 与 `unreleased` 记录
- 原做法：容易滑向两种极端，要么完全不记未发布变更，要么倾向“每修完一个问题就 commit 一次”
- 更优做法：每完成一个**已验证的语义修复批次**，默认更新 `changelogs/unreleased.md`；`commit` 不自动按“问题个数”切分，而是按**语义批次**提交，仅在用户明确要求、需要独立回滚点、或边界清晰且已闭环时再提交
- 改进收益：既保留未发布变更追溯，又避免产生大量碎片化 commit；更符合回滚、审阅和 release 归档的真实边界
- 状态：已纳入规范（待同步到提交/文档同步/发布边界相关规则）

## PI-010
- 发现时间：2026-05-25
- 场景：用户确认后进入下一阶段前，尤其是控制面规则、多文件联动、真相源同步场景的前置复审
- 原做法：前置复审虽已存在，但容易停留在内部自检，既不稳定显式输出，也未强制交叉验证
- 更优做法：前置复审结果必须显式输出；当场景涉及控制面规则、多文件联动、真相源同步、模板/示例/校验链联动时，必须追加交叉验证，并在发现阻断项时先修正当前产物再重新确认
- 改进收益：能显著降低“带着阻断项继续推进”的概率，也能把规则、示例和校验链漂移更早拦住
- 状态：已纳入规范（待同步到 common / cp-gate / dev / fix 主规则）

## PI-011
- 发现时间：2026-05-25
- 场景：多项目工作区中，开发/修复完成后虽已写入 `changelogs/unreleased.md`，但若没有本地 `commit`，缺少明确回滚锚点与 commit hash 追溯
- 原做法：默认只更新 `unreleased`，`commit` 仍停留在“看情况是否执行”的弱约束
- 更优做法：每完成一个**已验证的语义变更批次**，默认建议执行**本地 `commit`** 作为回滚锚点，但仍不默认 `push/tag/publish`
- 改进收益：既保留未发布阶段的低风险节奏，又补齐本地回滚、diff 定位与批次追溯能力
- 状态：已纳入规范（提交边界已收口，待本轮实现完成后按批次执行）

## PI-012
- 发现时间：2026-05-25
- 场景：执行中临时发现的规范/流程问题，若一律“发现即修”，容易把主任务切碎并造成范围漂移
- 原做法：阻断项与非阻断项缺少统一分流，临时发现的问题常直接穿插进入当前会话修复
- 更优做法：阻断项即时修复；非阻断项统一进入 `data/pending-issues.md`，按批次进入需求或 bug 修复流程
- 改进收益：能稳定主任务边界，降低会话漂移，同时保留后续持续优化的入口
- 状态：已纳入规范（问题池机制已建立）

## PI-013
- 发现时间：2026-05-26
- 场景：审查/复审报告从“深度逐文件审查”收敛到“问题总清单”时，如何既保留修复优先级，又不丢失逐文件异常落点
- 原做法：问题总清单只保留根因级问题，把逐文件问题全部压缩进抽象归类，导致用户看到“深度审查里有问题，总清单里却没有完整展开”
- 更优做法：审查类汇总报告默认采用“两层清单”：先列根因级问题用于确定修复顺序，再展开逐文件完整落点并标注对应根因，边界/非缺陷结论单独列示，不混入缺陷编号
- 改进收益：既能保持修复批次清晰，也能避免文件级问题在汇总阶段被吞掉，便于用户确认范围与实施时逐项核销
- 状态：已记录，待同步到审查/报告规范
