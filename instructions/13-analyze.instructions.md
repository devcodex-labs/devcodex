# 分析工作流规则（13-analyze）

> 本文件定义 analyze 工作流的完整规则，含 research 子类型。

## 核心约束

### 只读约束
- **analyze 是只读工作流**：禁止修改任何源码文件
- 需要修改时 → 在报告中建议切换 dev 或 fix 工作流

### 单轮分析约束
- analyze 为单轮分析工作流，输出结论/报告即完成
- **不进行多轮收敛**（区别于 audit）

### 三项验证（必须附在每条结论上）
1. **合理性** — 依据是什么？
2. **可实施性** — 能否落地？前置条件？
3. **收益** — 执行后带来什么改善？

> ⚠️ 三项验证必须在**用户面结论**中可见，不得仅在报告文件中满足。
> ⛔ 缺少任意一项验证均导致 SC1 不通过。

### 影响评估触发
- 分析结论涉及架构/方案影响时 → 执行六维影响评估
- 无架构影响时 → 直接输出报告

## 子类型

### default（单轮分析）
- 直接执行分析，输出结论
- 推荐使用短格式：`结论 + 合理性 + 可实施性 + 收益`（必要时补充验证状态与影响范围）

### research（技术调研）

> ⚠️ 执行 `analyze.research` 时，须按 `01-common` §Skill 按需读取表读取 `analyze-research` Skill 获取详细调研规范。

**触发条件**：用户要求调研/评估/比较某技术方案

| 场景 | 示例 |
|------|------|
| 技术选型 | "对比 Redis/Memcached，推荐缓存方案" |
| 可行性评估 | "评估引入 GraphQL 的成本和收益" |
| 根因调查 | "找出导致内存持续增长的根因" |

**执行流程**：
1. 明确调研问题（一句话核心问题）
2. 确认调研范围（深度 + 技术栈约束）
3. 收集信息（profile + 源码 + 依赖文档）
4. 分析评估
5. 三项验证
6. 输出明确结论（禁止模糊结论）
7. 输出调研报告

**输出格式**：
- 技术选型：推荐方案 + 理由 + 注意事项
- 可行性评估：结论 + 前置条件 + 成本估算 + 风险点 + 备选方案
- 根因调查：现象 + 根因链路 + 影响范围 + 修复建议 + 预防措施
