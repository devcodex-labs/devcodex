# 分析工作流规则（13-analyze）

> 子类型标识：`analyze.default` / `analyze.research`

> 本文件定义 analyze 工作流的完整规则，含 research 子类型。

## 核心约束

### 只读约束
- **analyze 是项目内容只读工作流**：禁止修改源码、规范与配置；允许写分析报告、记忆，以及经 `spec-governance` 语义分流后必须写入的 active-root 运行态台账
- 需要修改时 → 在报告中建议切换 dev 或 fix 工作流
- 用户先给出结论、根因或方案假设时，analyze 仍须独立取证；若核验后结论成立，可直接采纳并说明证据，禁止为了表现“独立”而机械反对

### 代码实现验证约束

> 🔴 **证据来源约束**（与 PCV-2 并列，全场景适用）  
> 当分析结论依赖"代码是否存在/如何实现"这一事实时，**无论用户如何表述请求**，必须先探索实际代码，再与计划/需求文档比对。

**强制探索顺序**：

| 步骤 | 正确做法 | 禁止做法 |
|:----:|---------|---------|
| 第 1 步 | **先 grep/glob 实际代码**：以功能关键词、接口路径、类名、方法名为搜索项，在代码库中主动探索 | ❌ 直接取计划/需求文档中的文件路径做存在性检查（`Test-Path`/`ls`）|
| 第 2 步 | **再与计划/需求对比**：将探索发现的实际实现与计划文档比对，识别完整实现/架构偏差/未实现 | ❌ 未找到计划路径对应文件即直接结论"未实现" |
| 第 3 步 | **标注偏差类型**：`✅ 按计划实现` / `⚠️ 架构偏差（功能完整，路径/结构不同）` / `❌ 未实现` | ❌ 将"架构偏差"误判为"未实现" |

> ⚠️ 计划文档描述的是**意图路径**，不是**事实路径**；实际开发可能合并、拆分或改名。以计划路径做存在性验证，会将架构调整误判为未实现。  
> ⛔ **触发判断不依赖用户措辞**，而是 AI 自检：「我的结论是否依赖代码事实？」→ 是 → 必须先探索代码。

### 多轮收敛约束

- analyze **执行多轮收敛**，最少 3 轮，直至连续 2 轮无新发现为止
- 🔴 "至少 3 轮"是硬性下限：即使前几轮已无新发现，仍须完成第 3 轮才可声明收敛
- 未收敛时自动进入下一轮，**不询问用户**
- 禁止提前收敛：不得在未达到最少轮次时输出"已收敛"结论

### 相关文件联查（analyze-lite）

- `analyze` 不直接复用完整 `audit` 流程，但必须补足最小联查动作
- 至少执行以下步骤：
  1. 提取本轮分析问题的核心关键词
  2. 建立关联文件集合（代码、规则、文档、验证产物，按问题类型选取）
  3. 分析过程中若发现高联动场景，默认升为 **L2 标准联查**
  4. 收敛前必须再跑一次 `CRS`，确认关联文件集合没有遗漏
- 若命中控制面、多真相源、模板-示例-校验链或单轮发现 ≥5 条 / 出现 🔴 问题，必须主动建议升级为 `audit`

> ℹ️ **analyze vs audit 的差异**：  
> - `analyze` — 聚焦**特定问题/结论**，不使用维度框架，轻量多轮（≥3 轮，连续 2 轮无新发现后收敛）  
> - `audit` — 使用**完整维度框架**（G1~G5 + 专属维度），覆盖范围更广；收敛条件：连续 3 轮有效零发现（仍须满足连续 3 轮零发现，并核验 `ReviewCoverageDelta`；不区分定向/全面，见 `12-audit §多轮收敛规则`）

### analyze → audit 升级触发
当 analyze 执行过程中出现以下任意情形时，**必须主动建议用户升级为 audit 工作流**：

| 触发条件 | 说明 | 升级建议 |
|---------|------|---------|
| 单轮新发现问题数量 ≥ 5 条 | 超出轻量分析可处理范围 | 建议升级 audit 全面体检（≥3 轮，连续 3 轮有效零发现）|
| 存在 🔴 级问题 | 高严重度需维度框架保障全面覆盖 | 建议升级 audit，确保多轮无遗漏 |
| 分析涉及多模块交叉影响 | 超出 analyze 的维度覆盖范围（analyze 不使用 G1~G5 + 专属维度框架）| 建议升级 audit |
| 用户明确要求"全面/深度/逐项" | 用户期望与 analyze 轻量定位不符 | 直接路由 audit，不进 analyze |

> ℹ️ 升级建议仅为**主动提示**，不强制中断当前 analyze 输出。用户确认升级后，本轮 analyze 结论可作为 audit R1 的初始输入。

### 三项验证（必须附在最终结论上）
1. **合理性** — 依据是什么？
2. **可实施性** — 能否落地？前置条件？
3. **收益** — 执行后带来什么改善？

> ⚠️ 三项验证通过 **PCV-3** 统一完成（而非每轮实时补充）；最终用户面结论中必须可见，不得仅在报告文件中满足。
> ⛔ 缺少任意一项验证均导致 SC1 不通过。

### 推荐结论（必须显式）

- analyze 报告或用户面结论出现多个可执行建议、多个后续路径或方案对比时，必须输出 `推荐结论` 或 `推荐方案`。
- 推荐结论必须包含“推荐理由”，且推荐理由能追溯到合理性、可实施性、收益、验证状态、影响范围五项验证。
- 若没有可推荐动作，必须显式写明 `推荐：无后续动作` 及原因，避免用户从建议列表中猜主路径。

### PostAssessmentGovernanceIntakeGate

- analyze 完成合理性评估与 PCV 事实复核后，必须对当前消息的中性 candidate 形成完整 `GovernanceIntakeDecision`；不得用用户措辞或关键词直接决定是否记录。
- 结论同时证明更优策略、规范缺口、既有违规或审查盲区时，保留全部 `record.*` 意图并逐项写入/验证；不能只取第一个分类。
- `record.none` 必须通过 `RecordNoneChallengeGate`；`record.ambiguous` 保持未终结并先澄清。analyze 报告同步记录 candidate ID、target ledger、write requirement/evidence 与 verification state。

### QuestionEvidenceGate / ComparativeResearchGate

- 用户没有直接说“调研/比较”，但问题本质是在问“是否应该”“哪个更好”“有没有更好建议”“推荐什么方案/工具/项目/产品”时，analyze 必须先判定 `QuestionEvidenceGate`，再决定是否升级为 `analyze.research` 或在当前轮补足对比证据。
- 命中高影响建议、技术选型、产品/项目路线、架构方案、外部平台能力或时间/金钱投入决策时，必须执行 `ComparativeResearchGate`：比较同类产品 / 项目 / 本仓库相似模块 / 已有设计，并在最终结论写明证据范围与 `N/A + skipReason`。
- 纯解释、低风险本地事实核验、用户明确要求快速答复且不影响高成本决策时，可标 `ComparativeResearchGate: N/A + skipReason`；不得为了“调研完整”把普通问答默认升级成多轮重调研。

### ReviewFindingIntakeGate / DesignIntentAndDocsConsistencyGate

- 当 analyze 输入是外部审查报告、AI review finding、audit issue 或代码评审发现时，报告内容只能作为线索，不能直接作为已验证结论。
- 每条 finding 必须先补本地证据并分类为 `must-fix` / `user-decision-required` / `docs-implementation-drift` / `test-coverage-gap` / `already-fixed-or-not-reproduced` / `intentional-design-accepted`。
- 命中 intentional design、兼容设计、性能取舍或产品策略时，应记录设计依据、消费者影响和文档/测试承托；命中用户决策项时，最终结论只能给确认问题，不得建议直接改源码。
- 文档与实现不一致时，需判断文档是否代表产品目标或历史承诺；测试覆盖不足时，优先建议补测试、复现脚本或验证证据。

### GovernanceGateRegistryRef 分析侧取证

- analyze.default 的执行细节由 `skills/analyze-default/SKILL.md` 承接；本文件只保留只读边界和工作流索引。
- non-small / 分批 / 增量 / 精度：加载 `skills/incremental-project-analysis/SKILL.md`（快照、BatchProgress、GlobalBacklog、双层验证）；规模路由仍用 `skill-gap-analysis`。
- 项目级 analyze 在形成结论前必须引用 `load-profile` 的 `ProfileTruthReconciliationGate` targeted 模式；低风险文件级分析可 `N/A + skipReason`。发现 Profile 漂移时只矫正当前结论，Profile 源修改必须切换独立 dev/fix/self-fix。
- 分析发现规范吸纳、完整吸纳补强、历史长清单迁移、复审遗漏、用户文档、前端运行态、发布门禁、Profile/service 规范或自我进化控制面问题时，不在 instructions 展开 Gate 长清单；必须引用 `skills/spec-governance/SKILL.md` 的 `GovernanceGateRegistry`。
- 分析返工率、兼容/迁移、配置复杂度或交互语义时，分别引用 `rework-prevention`、`contract-release-authority`、`configuration-ergonomics`、`interactive-semantics`；分析结论不得把历史基线、未发布草稿、实现字段存在或截图当作效果/权威/易用/可访问性完成证据。
- 分析完整 Agent 平台、文档受众渲染顺序、跨仓消费者验证或逐模块性能维护时，分别引用 `agent-capability-completeness`、`docs-audience-render-sequence`、`consumer-validation`、`module-performance-maintenance`；结论必须受声明对象、运行态/身份链、适用分母与新鲜度约束。
- 分析报告只写 `gateGroup / ownerSkill / trigger / evidence / validationRoute / skipReason`。分析阶段保持只读，等待用户确认后再切换 dev/fix/self-fix 实施。

### 收敛后汇总验证（PCV）

> 🔴 强制步骤：所有轮次收敛后，必须执行 PCV，方可输出最终报告。

| 步骤 | 动作 |
|------|------|
| PCV-1 汇总去重 | 汇总所有轮次发现的问题/结论，去除轮次间重复条目 |
| PCV-2 实证核查 | 对每条结论/问题，**重新读取**对应文件/代码位置，确认描述准确（不得仅凭记忆）。**若结论依赖运行时数据**（测试通过率、性能数字、API 响应等），**优先本轮实际执行**对应命令取得当前结果；无法执行时标注 ⚠️待验证（须注明来源为历史记录）；禁止将记忆文件历史数据直接标注为 ✅已验证 |
| PCV-3 三列验证 | 为每条已确认结论补充：合理性（依据）+ 可实施性（前置条件）+ 收益（改善效果）|
| PCV-4 推荐结论 | 多建议/多路径时选出 1 个推荐方案并说明推荐理由；命中 `QuestionEvidenceGate` 时同步记录 `ComparativeResearchGate` 证据范围或 `N/A + skipReason`；无推荐动作时写明原因 |
| PCV-5 分级标注 | ✅已验证（有实证）/ ⚠️待验证（推断，需用户确认）/ ❌排除（证据不支持，移除）|
| PCV-6 最终输出 | 输出过滤后的最终结论；❌排除 项须说明排除原因 |

> ⚠️ **记忆文件 ≠ ✅已验证依据**：SUMMARY.md、每日记忆文件是**上下文背景**，不是本轮分析实证。运行时历史数字（测试通过率/性能数字等）**优先本轮重新执行**验证；无法执行时标注 ⚠️待验证（注明来源为历史记录）；禁止直接引用为已确认结论。用户明确要求基于历史数据分析时，整体结论须标注 ⚠️基于历史数据，并建议执行验证后确认。

### 影响评估触发
- **PCV 完成后**，若最终结论涉及架构/方案影响时 → 执行六维影响评估（不在每轮触发，在 PCV 通过后一次性执行）
- 无架构影响时 → 直接输出报告

## 子类型

### default（分析工作流）
- 至少执行 **3 轮**分析，连续 2 轮无新发现后收敛
- 每轮聚焦上轮遗漏的角度或未验证的结论
- 推荐每轮格式：`结论要点（合理性/可实施性/收益简注）`（每轮为轻量笔记，完整三列验证在 PCV-3 统一完成）
- 轮次末尾输出收敛状态：`第 N 轮 | 新发现 M 项 | 是否收敛？✅/⏳`

### research（技术调研）

> ⚠️ 执行 `analyze.research` 时，须按 `01-common` §Skill 按需读取表读取 `analyze-research` Skill 获取详细调研规范。

**触发条件**：用户要求调研/评估/比较某技术方案

| 场景 | 示例 |
|------|------|
| 技术选型 | "对比 Redis/Memcached，推荐缓存方案" |
| 可行性评估 | "评估引入 GraphQL 的成本和收益" |
| 根因调查 | "找出导致内存持续增长的根因" |

**执行流程**：
1. 明确调研问题（一句话核心问题）
2. 确认调研范围（深度 + 技术栈约束）
3. 收集信息（profile + 本仓库上下文 + 同类产品 / 项目 / 模块对比 + 官方文档优先 + 其他资料降级）
4. 分析评估（**至少 3 轮**，每轮从不同角度补充验证；连续 2 轮无新发现后收敛；每轮末尾输出：`第 N 轮 | 新发现 M 项 | 是否收敛？✅/⏳`）
5. **PCV（收敛后汇总验证）**— 见核心约束 §收敛后汇总验证；三列验证在 PCV-3 完成，禁止跳过
6. 输出明确结论（禁止模糊结论，结论从 PCV-6 最终输出获取）
7. 输出调研报告

**资料优先级**：
- 当问题涉及平台能力、框架 API、版本兼容性、弃用项、第三方工具参数或命令语义时，优先读取官方文档或官方参考资料。
- 若官方文档不存在，再降级到官方源码 / 官方仓库说明、项目内文档、社区资料。
- 本地纯实现问题或可直接由仓库事实闭环验证的问题，不强制触发官方文档前置步骤。

**输出格式**：
- 技术选型：推荐方案 + 理由 + 注意事项
- 可行性评估：结论 + 前置条件 + 成本估算 + 风险点 + 备选方案
- 根因调查：现象 + 根因链路 + 影响范围 + 修复建议 + 预防措施
