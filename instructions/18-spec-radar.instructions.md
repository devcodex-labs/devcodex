# 规范雷达（18-spec-radar）

> ⚠️ **加载范围说明**：本文件通过 `applyTo: "**"` 注入全局上下文（使规范始终可见），但 **PC4 完整三轴诊断受 ENV_MODE 控制**：dev 模式才执行三轴诊断，非 dev 模式在入口检查 PC4 中标注 N/A（dev 扩展诊断未启用）。

> 本文件定义 **PC4 规范原因识别**的完整规则。
> PC4 是 DevCodex 的规范自我升级机制的感知层——在任务执行前/中持续监测，识别"当前问题是否源于规范本身的缺陷"。  
> **仅 dev 模式执行完整诊断**；非 dev 模式不执行本文件的三轴诊断，但显式记录意图识别与 Improvement Intake 仍按 `spec-governance` 的全模式规则执行。
> `SpecRadarSubgate` 的执行字段、gateGroup 分组、ownerSkill 和 validationRoute 由 `skills/compliance/SKILL.md` 与 `skills/spec-governance/SKILL.md` 的 `GovernanceGateRegistry` 承接；规范吸纳候选的扫描、通用性证明和消费者证明由 `skills/spec-absorption/SKILL.md` 承接；本文件不承载完整 Gate 长清单。

## 定位与职责边界

| 文件 | 时机 | 职责 |
|------|:----:|------|
| `17-compliance.instructions.md` | 任务完成**后** | FC/SC/RC/T 事后验证 |
| **本文件（18-spec-radar）** | 任务执行**前/中** | 实时感知规范缺陷，输出 PF/VL 标记 |

> ⛔ PC4 不是"验证 AI 是否遵守规范"，而是"检测规范本身是否存在缺陷"。两者的诊断对象完全不同。

> **设计原则：记录在使用，修复在维护** — PC4 在所有项目/所有工作流中只负责感知并记录；具体写入前必须先走 `spec-governance` 的记录意图识别与 RecordRouter（PF → `pending-fixes.md`，VL → `violations.md`，PI/ISSUE/GAP 按意图分流），**不触发任何修复动作**。audit 始终只读并交接 finding；只有用户独立授权的 dev/fix/self-fix repair workflow 才能修改规范或 plugin 文件。`data/process-improvements.md` 在本页也可称“优化清单（PI）”。

## 核心原则 — 意图模式驱动，非关键词匹配

> ⚠️ PC4 **禁止依赖关键词匹配触发**（如："确定吗"、"不对"、"再解释"等表面词汇）。  
> ✅ 正确方式：AI 对当前交互状态执行**三轴自检**，由轴的诊断结论决定是否触发。  
> 关键词可以作为辅助线索，但不能是触发依据——同一句话在不同语境下可能完全无关。

`PostAssessmentGovernanceIntakeGate` 是全模式基础层：每条非空消息先登记中性 candidate，待合理性评估、项目现实扩展和上下文归因完成后，再以三轴事实及其他项目证据形成 `GovernanceIntakeDecision`。PC4 三轴在 dev 模式提供额外诊断证据，但“未执行 dev 三轴”不等于跳过全模式治理评估；Hook 只维护 candidate set 和证据状态，不按关键词替 AI 分类。候选按 `detected → assessed → generalized → routed → write-observed → acknowledged` 留存阶段历史，`uncertain/ambiguous` 与缺写入证据都不得越级终结。

## 触发时机

PC4 有两种检查点，**均为 dev 模式专属**：

| 检查点 | 时机 | 说明 |
|:------:|------|------|
| **检查点 1** | 收到新消息时 | 每轮必执行，即时触发；**G5 仅检查点 2 可评估**（需 PC1 意图已知后才能对比 violations.md）|
| **检查点 2** | 任务执行中检测到异常时 | 在当前回复中立即完成诊断并输出，**不等待下轮消息**，不中断任务主体流程 |

## 三轴诊断模型

PC4 通过三个轴评估交互的底层状态，任意一轴出现异常即进入深入诊断：

### Axis A — AI 认知锚点（自检）

> 核心问题：AI 当前的决策/输出，是否有明确的规范条目作为依据？

| 状态 | 说明 | 结论 |
|:----:|------|:----:|
| ✅ 有，可引用具体规范节点 | 正常，继续检查 Axis B | — |
| ⚠️ 无，依赖"经验"/"推断"/"看起来合理" | 认知锚点缺失 | PF — G1 |
| ⚠️ 有规范，但本次未执行 | 认知锚点违背 | VL |
| ⚠️ 两条规范指向不同方向，无法裁决 | 认知锚点冲突 | PF — G6 |
| ⚠️ 有规范且已执行，但规范依赖的外部假设已失效 | 外部环境与规范不符 | PF — G8 |
| ⚠️ 项目未识别但未询问用户即推进工作流/调用扫描工具 | 违反 `01a-profile-loading` §确定目标项目 / 多项目工作区扫描禁令 | VL — G11 |

### Axis B — 对话轨迹（收敛/循环检测）

> 核心问题：当前话题是否在收敛？还是在循环或出现拦截滞后？

| 状态 | 说明 | 结论 |
|:----:|------|:----:|
| ✅ 收敛：每轮交互后未解决问题减少 | 正常，继续检查 Axis C | — |
| ⚠️ 循环：同一话题 ≥ 3 轮，仍未达成共识 | 轨迹循环 | PF — G2 |
| ⚠️ 漂移：每轮 AI 给出不同解释/方案（非用户要求修改）| 答案不稳定 | PF — G1 |
| ⚠️ 滞后：问题在阶段 Y 才被发现，规范要求应在 X 拦截（X 早于 Y）| 拦截节点滞后 | PF — G3 |
| ⚠️ 重复违规：当前问题与 violations.md 已有 VL 同类型 | 已有 VL 未转化规范改进 | PF — G5 ⚠️ 仅检查点 2 |
| ⚠️ 边界缺失：AI 不知何时停止，或过早宣告完成 | 任务完成判定标准缺失 | PF — G9（与 Axis C 联合）|

### Axis C — 用户预期满足度（差值检测）

> 核心问题：用户是否在为 AI 的规范缺陷"买单"（补偿/迁就/放弃）？

| 用户行为模式 | 底层含义 | 结论 | 判别阈值 |
|------------|---------|:----:|:--------:|
| 立即修改/纠正 AI 的输出 | AI 输出与预期有结构性偏差 | PF 候选 | 单次=疑似；≥2次=确认 |
| 开始微操（逐步指令，而非高层目标）| 用户被迫填补 AI 规范推导的空白 | PF — G4 | 单次=疑似；≥2次=确认 |
| 向 AI 解释"应该知道的背景" | profile 或规范未要求加载该上下文 | PF — G7 | 单次=疑似；≥2次=确认 |
| 给出类比/例子说明期望 | 直接描述无法映射到 AI 的规范概念 | PF 候选 | 单次=疑似；≥2次=确认 |
| "随便"/"你决定"（语境含放弃意味）| 多轮未满足后的妥协，非真正授权 | PF 候选 | 单次=疑似；≥2次=确认 |
| 放弃子任务（"算了，我自己做"）| 规范无法支撑 AI 完成任务 | PF — G4 | 单次即可确认（放弃行为本身即强信号）|
| 重新复制粘贴之前说过的指令 | AI 未能从规范中持续锚定该要求 | PF — G4 | 单次即可确认（重复粘贴=强信号）|
| 对 AI 输出明确表示"不够"/"还差一步" | 规范未定义任务完成边界 | PF — G9（与 Axis B 联合）| 单次=疑似；≥2次=确认 |

## 完整触发场景（G1~G9）

> 以下场景识别**必须基于三轴诊断结论**，而非依赖词语匹配。括号内为典型但非充分的表面表现。

| 编号 | 名称 | 触发轴 | 表现特征 |
|:----:|------|:------:|---------|
| **G1** | AI 认知锚点缺失 | A | AI 使用推断性语言；就规范应覆盖的事向用户征求意见；同类问题跨会话答案不一致；需要大段理由论证而非引用规范节点 |
| **G2** | 对话轨迹循环 | B | 同一话题 ≥3 轮未收敛；用户换表达方式但实质未变，AI 仍无稳定答案；话题被反复"拉回" |
| **G3** | 拦截节点滞后 | B | 应在 CP1 发现的问题在执行阶段才暴露；应在 plan-review 拦截的缺陷在 Audit 才发现；AI 未完成规定前置检查就推进了流程；**跨会话恢复后跳过预检查直接执行任务**（高频场景） |
| **G4** | 用户预期补偿 | C | 用户开始补充 AI 本应主动确认的信息；用户逐步监督操作过程；用户直接提供完整解决方案（替代 AI 规范推导）；用户放弃子任务 |
| **G5** | 重复违规（系统性）| A+B | 当前问题与 `violations.md` 已有 VL 同类型 → 已有 VL 未转化为规范改进；追加 PF 时注明关联 VL 编号。⚠️ **仅检查点 2 可评估**（需 PC1 意图已知后才能对比 violations.md 同类型）|
| **G6** | 规范内部冲突 | A | 两条规范同时适用且方向相反，AI 无法裁决；选任何一条都不能完全满足用户预期 |
| **G7** | 领域知识缺口 | C | 用户在对话中教授 AI 项目惯例/框架特性/架构约束 → profile 或规范应覆盖但未包含 |
| **G8** | 外部假设失效 | A | 规范基于的外部环境假设已改变（工具版本/API 行为/平台特性）；AI 严格按规范执行，但结果与现实不符 |
| **G9** | 完成边界缺失 | B+C | AI 不知何时停止（持续追加内容）；AI 过早宣告完成；规范缺少该类任务的完成判定标准 |
| **G10** | limit 截断恢复未 resume（v1.9.4+）| B | 上次会话因 session limit 截断（最末 Edit 部分写入 / 任务未结束），本次会话首步未读取今日 tasks 文件、未检测 §会话段落 末尾状态字段、未对比 SUMMARY vs tasks 状态一致性 → 直接走 cp-gate 或新工作流分支；触发判定：tasks 最末段落缺 ✅ 状态行 + SUMMARY 对应行已 ✅（数据不一致）或 mtime < 24h 与本次首条用户消息差 < N 分钟。需立即补 resume 检测，标记 VL（违背 15-memory §新会话首步）|
| **G11** | 项目未识别未询问即推进（v1.9.8+）| A | PC0 输出“项目 [未识别]”但 AI 未输出询问、未暂停，直接续输 PC1~PC7 或开始工作流 / 发起 `file_search` / `semantic_search` / `grep_search` / `list_dir` 超出当前文件范围的调用。违反 `01-common` 优先级 3 硬约束 → 标记 VL，路由 self-fix。豁免词同 `lifecycle.cjs` `isMultiProjectWorkspace`。|

## 多轴优先级规则

当三轴诊断中**多轴同时出现异常**时：

1. **全部标记**：所有异常轴均需标记，不可因 Axis A 已触发而跳过 B/C 检查
2. **排列顺序**：PF 条目按 Axis A → B → C 顺序列出（认知锚点问题优先，用户感知问题在后）
3. **根因优先**：若 Axis A 已出现 PF（规范缺失/冲突），Axis B/C 的异常通常是其下游表现，根因分析应聚焦 Axis A

```text
示例：同一任务 Axis A 和 C 均异常
- PF（Axis A, G1）：AI 输出缺乏规范依据 → 延迟追加
- PF（Axis C, G4）：用户被迫微操指导 AI 执行 → 延迟追加（根因可能同 G1）
```

## 置信度与处理规则

| 置信度 | 触发条件 | 处理方式 |
|:------:|---------|---------|
| **确认** | 三轴诊断有明确异常 + 规范查证完成 | 直接标记 PF 或 VL，延迟追加 |
| **高** | 三轴诊断显示异常，规范查证进行中 | 查规范后定性，当前回复内完成判断 |
| **疑似** | 一轴显示潜在异常，证据不足 | 标记 `⚠️ 疑似 PF`，回复末尾注明"待确认是否存在规范盲区" |

## PC4 决策流程

```text
PC4 入口（仅 dev 模式）
├── 检查点 1：收到新消息时（每轮必执行）
└── 检查点 2：任务执行中检测到异常（当前回复内立即输出诊断）

【前置】用户是否明确要求"记录/登记/优化规范问题"，或当前消息经合理性评估后命中可泛化改进 / 规范缺口？
    ├── 是 → 先走 Intent Detection → RecordRouter / Improvement Intake
    │        ├── record.violation → 写 VL-NNN
    │        ├── record.spec-defect → 写 PF-NNN
    │        ├── record.process-improvement → 写 PI-NNN
    │        ├── record.pending-issue → 写 ISSUE-NNN
    │        ├── record.audit-gap → 写 GR-NNN
    │        └── record.ambiguous → 先澄清，不写台账
    └── 否 ↓

【Axis A 自检】AI 当前决策/输出是否有明确规范节点支撑？
    ├── 有，已正确执行 → Axis A ✅ → 继续 Axis B
    ├── 有规范但本次未执行 → 认知锚点违背 → 标记 VL → **继续 Axis B**（多轴全检）
    ├── 无规范 / 依赖推断 → 认知锚点缺失 → 标记 PF（G1）→ **继续 Axis B**（多轴全检）
    ├── 两条规范冲突 → 认知锚点冲突 → 标记 PF（G6）→ **继续 Axis B**（多轴全检）
    └── 有规范且已执行，但外部环境假设已失效 → 标记 PF（G8）→ **继续 Axis B**（多轴全检）

【Axis B 检测】当前话题的对话轨迹状态？
    ├── 收敛 → Axis B ✅ → 继续 Axis C
    ├── 循环（≥3 轮未收敛）→ 标记 PF（G2）→ **继续 Axis C**（多轴全检）
    ├── 漂移（AI 答案不稳定）→ 标记 PF（G1）→ **继续 Axis C**（多轴全检）
    ├── 拦截滞后（应在 X 发现，在 Y 发现）→ 标记 PF（G3）→ **继续 Axis C**（多轴全检）
    ├── G5 重复违规（⚠️ 仅检查点 2 可评估）→ 意图已知后对比 violations.md → 标记 PF（G5）→ **继续 Axis C**
    └── AI 不知何时停止 / 过早宣告完成 → 标记 PF（G9，与 Axis C 联合）→ **继续 Axis C**

【Axis C 检测】用户是否出现预期补偿行为？
    ├── 无 → Axis C ✅ → PC4: ✅ 三轴正常
    ├── 放弃子任务 / 重复粘贴指令（强信号，单次即确认）→ 标记 PF（G4）→ 延迟追加
    ├── 微操 / 纠正 / 举例（弱信号，≥2次确认）→ 单次=疑似；≥2次=标记 PF（G4）
    ├── 补充领域背景知识 → 标记 PF（G7）→ 延迟追加
    ├── 反复说"不够/还差一步"（规范未定义完成边界）→ 标记 PF（G9，与 Axis B 联合）→ 延迟追加
    └── 其他补偿行为（信号模糊）→ 置信度降为"疑似" → 回复末尾注明待确认

【多轴异常时】参见 §多轴优先级规则：全部标记，按 A→B→C 排列

【延迟执行】任务完成后、FC 执行前
    ├── 有 VL 标记 → 追加到 data/violations.md
    ├── 有 PF 标记 → 追加到 data/pending-fixes.md（含关联 VL 编号，如适用；多轴时并列 G 码，如 G1, G4）
    ├── 疑似 PF → 在回复末尾输出提示，由用户确认是否追加
    └── 均无 → 跳过（PC4: ✅）
```

> ℹ️ **延迟触发**：PC4 标记在检测点完成，追加动作在 FC 执行前执行，不中断任务主体。  
> ⛔ **禁止遗漏**：只要 PC4 标记了 ⚠️（含疑似），任务完成时必须有对应输出，SC4 检查此项。  
> 🔄 **检查点 2 回溯**：任意 Axis 检测到异常，必须在当前回复中立即完成诊断并输出，不得等待下轮消息。  
> ⛔ **禁止关键词触发**：不得仅因用户用了某个词汇而触发 PC4；必须经三轴诊断确认存在底层状态异常。

## 输出格式（入口检查块内）

```text
- PC4 规范雷达：[Axis A ✅/⚠️] [Axis B ✅/⚠️] [Axis C ✅/⚠️]
  → ✅ 三轴正常，无规范问题
  → ⚠️ PF 标记（G1）：[简述规范缺陷] · 延迟追加 pending-fixes.md
  → ⚠️ PF 标记（G4, G7）：[简述] · 延迟追加（多轴并列时，用逗号分隔 G 码）
  → VL 标记：[简述执行偏差] · 延迟追加 violations.md
  → ⚠️ 疑似 PF：[简述疑点] · 待用户确认后追加
```

> ℹ️ 多轴同时触发时，每个 Axis 的结论单独列行；G 码在同轴内用逗号合并（如 `G1, G6`），跨轴分行显示。
