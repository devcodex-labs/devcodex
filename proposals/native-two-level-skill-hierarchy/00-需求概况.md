## 1. 需求背景

DevCodex v1.20.7 已经实现一套独立的 Skill 管理、发现、索引、依赖解析、渐进加载、路由、生命周期和多宿主部署体系。

当前 Skill 源码采用扁平目录：

~~~text
content/skills/
├── intent/
│   └── SKILL.md
├── dev-default/
│   └── SKILL.md
├── audit-common/
│   └── SKILL.md
└── ...
~~~

目前宿主逐步具备原生 Agent Skills 能力，部分宿主也能发现嵌套 Skill。DevCodex 需要重新审视原有自建发现和路由机制，避免重复实现宿主已经提供的能力，同时保留宿主没有提供的任务治理、依赖、阶段控制、验证和证据能力。

本需求不是简单调整目录。当前多个源码、生成器、运行时、部署和验证模块都假设 Skill 是扁平结构。若只移动文件，可能出现 Skill 未注册、子 Skill 无法发现、intent.json 找不到、依赖解析失败、灰度状态过滤错误、部署漏文件以及 staged validation 与 worktree 结果不一致等问题。

本次目标是在不破坏 v1.20.7 已有能力的前提下，建立严格两层的物理嵌套结构，并让 DevCodex 内部运行时和不同宿主都能正确处理。

## 2. 已确认的结构约束

以下约束来自用户在本会话中的明确确认，属于本需求基线。

### 2.1 只允许两层 Skill

第一层是当前主 Skill，第二层是主 Skill 目录下固定的 skills 子目录中的子 Skill。

~~~text
content/skills/
└── parent-skill/
    ├── SKILL.md
    ├── intent.json
    ├── references/
    ├── scripts/
    └── skills/
        ├── child-skill-a/
        │   ├── SKILL.md
        │   ├── intent.json
        │   └── references/
        └── child-skill-b/
            └── SKILL.md
~~~

### 2.2 明确禁止第三层

以下结构禁止：

~~~text
content/skills/parent-skill/skills/child-skill/skills/grandchild-skill/SKILL.md
~~~

禁止递归创建 Skill 层级，也禁止通过别名、软链接或额外目录变相引入第三层。

### 2.3 普通资源目录不计入 Skill 层级

主 Skill 和子 Skill 自身仍可拥有 references、scripts、assets、agents 等普通资源目录。它们不是 Skill 层级。

子 Skill 内不得再出现用于承载其他 Skill 的 skills 目录。

### 2.4 采用物理嵌套，不采用扁平目录作为唯一源码结构

本需求采用 A 方案：子 Skill 的规范源码物理放在父 Skill 的 skills 目录下。

宿主不支持嵌套发现时，可以由部署适配器生成宿主专用投影，但不得因此改变 DevCodex 的规范源码布局，也不得形成多份人工维护的 Skill 源码。

### 3.5 当前部署模式

v1.20.7 的 Skill 部署模式默认为 hidden：

- Hidden：Skill 随不可变 Runtime Generation 部署，DevCodex 自己的运行时负责发现、索引和加载。
- Legacy：部署可见 Skill 树，允许宿主原生扫描。

本次不能为了利用宿主原生子 Skill 能力而默认关闭 hidden runtime，也不能破坏旧 generation 的读取连续性。

## 4. 核心问题与影响

### 4.1 目录层级不是唯一问题

若只移动 Skill 文件，以下链路仍会失败：

1. Bundle 无法正确识别嵌套 Skill。
2. Portfolio 可能无法正确生成子 Skill 注册和身份。
3. staged/index 模式可能漏掉子 Skill。
4. intent.json 和 DevCodex sidecar 无法按子 Skill 真实路径读取。
5. Runtime Identity Index 无法枚举子 Skill。
6. resolveSkillRead 无法通过子 Skill ID 精确解析。
7. 子 Skill 的 references/scripts/assets 可能使用错误根目录。
8. 生命周期过滤可能把父 Skill 的状态错误地应用到所有子 Skill。
9. 宿主不支持嵌套发现时，原生目录投影可能不可用。
10. npm package、安装升级、运行时 generation、回滚和公开 Skill Catalog 都需要同步。

### 4.2 父子关系与依赖关系必须分离

两者语义不同：

| 关系 | 含义 | 是否自动加载 |
|---|---|---|
| Parent / Child | 物理组织和能力归属关系 | 否 |
| requires | 执行某个 Skill 必须加载的依赖 | 是，按既有依赖规则 |
| conflictsWith | 不允许同时组合的 Skill | 否，作为组合约束 |
| references | 普通内容引用 | 否，按需读取 |

禁止因为 child 位于 parent/skills 下，就把 child 自动加入 parent 的 requires。

### 4.3 宿主原生发现与 DevCodex 自身发现必须分开

- 宿主原生发现：宿主是否能将嵌套目录中的 SKILL.md 注册成独立 Skill。
- DevCodex 自身发现：DevCodex 能否通过 Skill ID 找到并加载规范源码。
- DevCodex Governance：是否满足依赖、阶段、预算、CP、任务状态、验证和证据要求。

三者不能混为一谈。即使某宿主不支持原生嵌套发现，DevCodex 仍必须能够通过自己的运行时发现和加载子 Skill。

## 5. 目标架构建议

### 5.1 规范源码布局

建议保留 content/skills 作为唯一规范源码根目录。

~~~text
content/skills/
├── parent-skill/
│   ├── SKILL.md
│   ├── intent.json
│   ├── devcodex.skill.json
│   ├── references/
│   ├── scripts/
│   └── skills/
│       ├── child-a/
│       │   ├── SKILL.md
│       │   ├── intent.json
│       │   ├── devcodex.skill.json
│       │   └── references/
│       └── child-b/
│           └── SKILL.md
└── standalone-skill/
    └── SKILL.md
~~~

第一层 Skill 可以是独立 Skill，也可以是拥有子 Skill 的父 Skill。不是所有 Skill 都必须拥有子 Skill。

### 5.2 Skill 身份模型

建议 Portfolio 升级后的 Skill 记录至少包含：

| 字段 | 说明 |
|---|---|
| skillId | 全局唯一稳定 ID，不因移动目录而变化 |
| sourcePath | 相对 content/skills 的真实规范源路径 |
| level | root 或 child |
| parentSkillId | root 为 null；child 指向唯一父 Skill |
| lifecycleState | 每个 Skill 独立的生命周期状态 |
| publicCategory | 继续使用现有四类公共分类 |
| requires | 既有强制依赖关系，不承载父子关系 |
| conflictsWith | 既有冲突关系 |
| intentPath | 根据 sourcePath 定位的 intent.json |
| sidecarPath | 根据 sourcePath 定位的 devcodex.skill.json |
| sourceDigest | 绑定实际 Skill 正文及其资源合同 |

约束：

- Skill ID 在全局范围唯一。
- 每个 child 只能有一个物理父 Skill。
- 子 Skill 可以被其他 Skill 通过 requires 或引用复用，但不得复制第二份源码。
- parentSkillId 不得自动成为 requires。
- parent 的子 Skill 列表优先由目录结构确定性派生，不维护容易漂移的第二份手工清单。
- 子 Skill 可以独立进入 Catalog、独立解析、独立加载。
- Parent 和 Child 的生命周期状态分别管理；不因物理包含关系自动级联修改。

### 5.3 子 Skill 加载语义

建议规则：

1. 选中 parent Skill，只加载 parent 正文。
2. 不自动加载 parent 下全部 child。
3. 根据当前任务意图、parent 指令、requires 或用户明确指定，再选择具体 child。
4. 用户明确指定 child Skill 时，允许直接按 child ID 精确解析，不强制先加载 parent。
5. child 的 requires 继续执行既有依赖闭包、冲突检查、预算和阶段规则。
6. parent-child 关系只用于组织、发现、路由提示和治理，不作为隐式权限或执行授权。

### 5.4 宿主适配策略

建议采用“规范源码嵌套 + 宿主能力投影”。

| 宿主能力 | 部署策略 |
|---|---|
| 已通过真实验证，支持本结构嵌套发现 | 保留两层嵌套结构 |
| 不支持嵌套发现 | 生成宿主专用扁平投影，将 child 输出到宿主可扫描的 Skill 根目录 |
| 能力未知或没有当前版本证据 | 不宣称支持；使用 DevCodex Runtime 或保守投影 |
| Hidden Runtime | 由 DevCodex 自身 Runtime 按 sourcePath 解析，不依赖宿主原生递归发现 |

投影要求：

- 扁平投影只是部署产物，不是第二份规范源码。
- 投影记录 sourcePath、targetPath、skillId、parentSkillId、hostVariant、hostVersion、sourceDigest 和 projectionDigest。
- 同一个 Skill ID 在同一宿主扫描根下只能有一个有效部署目标。
- 不能静默覆盖用户已有的同名 Skill。
- 未通过宿主真实发现测试的能力必须标记 UNVERIFIED。

### 5.5 DevCodex 自身 Skill Runtime

Runtime 必须统一使用 Skill Identity Index 提供的真实路径映射：

~~~text
skillId
   │
   ▼
Runtime Skill Identity Index
   │
   ├── sourcePath
   ├── parentSkillId
   ├── level
   ├── lifecycleState
   ├── intentPath
   └── sidecarPath
          │
          ▼
   Exact Skill Resolver
          │
          ▼
   Skill Body / Resources
~~~

不得让各模块自行拼接 parent/child 文件路径。

## 6. 功能需求

### FR-01：两层目录结构校验

- 支持第一层独立 Skill 和父 Skill。
- 支持父 Skill 下固定 skills/ 子目录中的第二层 child Skill。
- 拒绝第三层 SKILL.md。
- 拒绝同一 Skill ID 重复注册。
- 拒绝没有有效父目录的 child。
- 拒绝 child 的 parentSkillId 与实际目录不一致。
- 目录深度、大小写、路径分隔符和 symlink/reparse 安全规则必须跨 Windows/Linux 一致。

### FR-02：Skill Portfolio 与注册

- Portfolio 能完整识别 root 和 child Skill。
- 每个 Skill 保留稳定 ID 和独立生命周期状态。
- plugin.json 注册路径能够表达嵌套 sourcePath。
- public taxonomy 必须继续精确覆盖所有已注册 Skill。
- 生成结果必须确定性，worktree 与 Git Index 结果一致。
- Portfolio Schema 需要升级策略，并提供旧版本读取/迁移兼容。

### FR-03：Intent 与 Sidecar

- intent.json 和 devcodex.skill.json 跟随各自 Skill，放在该 Skill 的目录内。
- 生成器通过 Skill 的真实 sourcePath 定位目标，不再按 ID 假设扁平目录。
- 资源相对路径以当前 Skill 根目录为边界。
- 保留当前路径穿越、symlink、文件大小、内容摘要和手工脚本调用约束。

### FR-04：Runtime 发现与精确解析

- Runtime 能发现第一层和第二层 Skill。
- Runtime 能按全局唯一 Skill ID 解析子 Skill。
- 项目、Workspace、Global 的覆盖优先级保持不变。
- 精确加载必须绑定当前 sourcePath、digest 和文件身份。
- 子 Skill 资源只能从自身 Skill 根目录解析。
- 不能因为父 Skill 存在而把 child 误认为已加载。

### FR-05：Catalog 与 Progressive Loading

- Catalog Card 增加 parentSkillId、level 等必要元数据。
- 子 Skill 可以进入模型候选列表并独立匹配。
- 父 Skill 不自动展开全部 child。
- 只加载最终选中的 Skill 和 requires 依赖闭包。
- 保留现有分页、预算、stage、状态、回放和 no-false-complete 约束。
- Parent-child 不得污染原有依赖图和依赖环检测。

### FR-06：生命周期与部署过滤

- 父 Skill 和子 Skill 的 active/gray/deprecated/retired/blocked 状态独立记录。
- 部署过滤按 Skill ID 和 sourcePath 判断，不能只看相对路径第一段。
- 父 Skill 不活跃时，不得在没有明确策略的情况下误删或屏蔽仍有效的 child。
- 部署、卸载和清理继续遵守现有 ownership receipt，不能删除用户自有目录或内容。

### FR-07：宿主能力适配

- 建立独立的 NativeSkillDiscoveryCapability 证据，不复用 Skill Route MCP 能力状态。
- 按 hostVariant、hostVersion、发现根、递归深度、实际发现结果记录证据。
- 对支持嵌套的宿主保留原结构。
- 对不支持或未验证的宿主生成兼容投影或使用 DevCodex Runtime。
- 不允许把文档声明、fixture 结果或 MCP 连通性直接标记为原生嵌套发现 PASS。

### FR-08：包构建和安装升级

- npm package 必须包含两层 Skill 源码和必要资源。
- prepack/postpack 投影必须支持嵌套 Skill。
- Hidden Runtime Generation 必须绑定完整 Skill Portfolio Digest。
- 升级时新 generation 与旧 generation 隔离，旧进程不得读到被覆盖的 Skill 内容。
- 安装失败、回滚、卸载和重复安装必须保持用户内容与旧运行时安全。

### FR-09：公开目录与文档

- 更新 Skill Catalog、Skill Reference、Host Guide、Progressive Skill Routing 文档。
- 对外明确区分原生 Skill 发现、DevCodex Runtime 发现和治理能力。
- 公开目录必须正确显示父子层级、分类、状态和可用性。
- 不得将未验证宿主能力写成已支持。

## 10. 待确认事项

以下是进入技术方案前需要确认的决策。本文件已给出推荐值，但未将推荐值伪装成用户已确认事实。

| 编号 | 决策 | 推荐方案 |
|---|---|---|
| Q1 | 两层目录规则适用范围 | 所有 DevCodex 管理的 package / global / workspace / project Skill；宿主自身管理的外部 Skill 不由 DevCodex 改目录 |
| Q2 | Child 是否可以独立调用 | 可以。Child 是独立 Skill ID，父子关系不要求先加载 Parent |
| Q3 | Parent 被加载时是否自动加载全部 Child | 不自动加载。仅按意图、显式选择和 requires 加载 |
| Q4 | Parent 与 Child 生命周期 | 各自独立；父 Skill 状态变化不自动级联改变子 Skill |
| Q5 | 不支持嵌套发现的宿主 | 由部署适配器生成扁平投影；规范源码仍保持嵌套 |
| Q6 | requires 与父子关系 | 完全分离；requires 仍表示强制加载依赖 |
| Q7 | 现有 87 个 Skill 如何分组 | 先按真实职责建立父子映射，不机械地把四个公共分类直接变成四个新父 Skill |
| Q8 | 是否立即移除旧 Skill Route | 不移除。先让 Runtime 支持新布局，再依据宿主实测逐步减少重复发现职责 |

### 建议的最终原则

1. 物理目录严格两层。
2. Skill ID 全局唯一，移动目录不改变 ID。
3. Parent-child 只表达组织和路由关系。
4. requires 只表达强制依赖。
5. Child 可以独立发现、独立加载。
6. Parent 不自动加载全部 Child。
7. 宿主原生发现按 Variant 和版本实测，不做统一假设。
8. DevCodex 继续负责宿主没有提供的治理、阶段、状态、预算、验证和证据。
9. 规范源码只有一份；不同宿主的差异通过生成投影解决。
10. 在用户确认需求和父子映射前，不批量移动现有 Skill，不修改运行时代码，不改变发布版本。
