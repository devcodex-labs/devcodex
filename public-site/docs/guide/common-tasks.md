# 常见任务

用户不需要背内部阶段。一个清楚的请求通常包含：目标、已知现象、范围与约束、验证要求，以及是否授权提交或发布。下面先给可直接使用的请求，再说明你应该看到什么。

## 先选择：直接使用宿主，还是使用 DevCodex

| 你的目标 | 建议 | 原因 |
|---|---|---|
| 问一个一次性问题、做短小编辑、依赖单个宿主的原生工具 | 直接使用宿主 | 更快，不需要项目状态、确认或验证链。 |
| 跨文件变更、需要先明确范围或验收 | 使用 DevCodex | 让项目上下文、专业 Skill 和确认边界按任务进入。 |
| 修复报错且担心同类回归 | 使用 DevCodex | 适合把复现、根因、同类检查和定向验证连起来。 |
| 需要换会话、换宿主或交给他人继续 | 使用 DevCodex | 任务状态、报告和记忆写在项目中，后续可以继续。 |

两者可以一起用：宿主继续提供模型和原生工具，DevCodex 只在需要工程流程增强时补上上下文、专业路径、验证和续接。

## 只读分析

```text
分析当前项目的主要问题，按优先级给出建议。只分析，不修改文件。
```

**应看到**：进入 `analyze`，说明读取范围，每个结论可追到证据，没有业务文件变化。若问题仍然含糊，使用[把模糊需求变成行动](/tutorials/ambiguous-request)。

## 开发功能

```text
为当前 API 增加请求幂等支持。先整理需求和验收标准，确认后实施并运行相关测试。
```

**应看到**：进入 `dev`，先形成目标、范围、非目标和验收条件；确认后才实施。跨前端、后端或公共契约时，使用[跨领域改动教程](/tutorials/cross-domain-change)。

## 修复问题

```text
复现支付回调重复入账，定位根因，检查同类路径并修复；只在相关测试通过后告诉我完成。
```

**应看到**：进入 `fix`，先保留复现证据，再说明根因、同类影响和回归路线；只会解释原因不算完成。完整路径见[修复并控制回归](/tutorials/fix-regression)。

## 审查现状

```text
从用户体验、架构、兼容性、测试和发布风险审查当前实现，只报告有证据的问题。
```

**应看到**：进入 `audit`；报告说明已读、抽样和未读范围。没有直接证据的判断保留为 `UNVERIFIED`，不会包装成已确认问题。

## 自动推进

```text
@devcodex-auto 修复失败的 CI，检查同类问题，运行完整验证，完成后提交。
```

`@devcodex-auto` 是正式名称；`@rocky` 是默认兼容快捷别名。明确写出 push、tag、npm publish 或 GitHub Release，才会把相应动作纳入本次授权范围。

auto 只自动通过适用的 CP，不会扩大项目范围，也不会豁免工作流有效性与验证；文件、删除和命令权限始终由宿主及其用户配置决定。第一次成功路径不需要 auto。

## 继续既有任务

```text
继续支付回调幂等任务
```

DevCodex 会尝试进入 `resume`，从项目报告、记忆和任务状态恢复，而不是凭对话片段猜测进度。

**应看到**：先核对任务身份、当前文件和原确认边界，再回到原工作流。完整交付模板见[带证据交付与续接](/tutorials/evidence-handoff)。

## 普通交流

不需要项目执行链的问答使用 `chat`。如果请求无法安全归类，`other` 只作为高级规划兜底；`self-fix` 只处理 DevCodex 自身流程问题。

## 请求没有按预期工作时

先看入口块里的项目、意图和下一步；再运行 `devcodex status` 与 `devcodex doctor`。不要用重复提示掩盖 Profile 缺失、adapter contract 失败或工作区识别错误。恢复路径见[故障排查](/guide/troubleshooting)。

完整集合与修改边界见[工作流参考](/reference/workflows)。
