# 修复问题并控制回归

这个教程用于“已经有报错或错误行为，但不能只改到不报错”的场景。

## 你将完成什么

- 建立可重复的故障现象。
- 区分表面症状与根因。
- 找出同类路径和回归范围。
- 用与风险匹配的测试证明修复结果。

## 前置条件

准备错误信息、复现步骤、受影响版本和最近改动。项目应已完成 DevCodex 初始化；不要把生产凭据或不可恢复操作当成复现前提。

## 发送这条请求

```text
修复“保存后页面仍显示旧数据”的问题。先复现并定位根因，检查同类缓存路径和消费者；给出修复边界与回归计划，确认后再修改。复现步骤：……；期望：……；实际：……。
```

## 预期工作流

任务应进入 `fix`。在修改前，DevCodex 会核对现象、证据、最近变更和受影响消费者；随后给出问题定义、修复方案和验证路线。低风险修复可以缩短产物，但不能跳过根因和验证。

## 写入边界与确认

诊断阶段保持只读。确认修复方案后才修改源文件；如果方案扩展为新功能、公共契约变化或大范围重构，应重新绑定为 `dev` 需求，而不是把范围塞进原 Bug。

## 可见结果

成功交付应包含：

- 可重复的失败证据；
- 根因及其与症状的因果关系；
- 修改文件和同类影响面；
- 修复前失败、修复后通过的验证；
- 未覆盖风险和回滚方式。

## 如果修复后仍不稳定

- 只能偶现：补充时间、并发、数据状态和环境差异，避免凭一次成功宣称完成。
- 测试通过但用户路径失败：增加真实页面或集成路径验证。
- 修改面不断扩大：停止写入，重新确认范围与契约。
