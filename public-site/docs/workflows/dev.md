# `dev`：开发与实施

新的主入口是 [开发与修复](/workflows/change)。本页保留 `/workflows/dev` 深链，并提供 `dev` 的阶段细节；完整 subtype 与 `dev.plan-review` 层级以分组页和[工作流索引](/reference/workflows)为准。

## 适用 / 不适用

适用：新功能、重构、按已确认需求写文档或改代码。  
不适用：只想听建议（用 [`analyze`](/workflows/analyze)）；已确认的缺陷修复（用 [`fix`](/workflows/fix)）。

## 是否改文件

会，但要经过需求确认。未确认前不应改业务源码。

## 阶段与检查点

1. **CP1 需求**：确认用户结果、范围、非目标、验收和消费者。
2. **CP2 方案**：确认模块职责、共享契约、风险、回滚和验证路线。
3. **条件 CP3 计划**：多文件、高风险或跨模块任务确认批次、依赖和停止条件。
4. **实施与 checkpoint**：按确认范围增量修改；批次间验证，不静默扩展需求。
5. **ECR**：对照需求、diff 和测试证据，写报告与续接状态。

低风险单文件任务可以缩短产物，但不能把 CP1 与 CP2 合并成一句“我准备这样改”。

## 确认边界

范围、公共契约、是否改哪些路径、是否提交或发布，都要在相应边界获得授权。auto 可以自动通过 CP，但不会自行扩大到 `push`、tag、发布、删除或项目外写入。

## 产物

需求确认、技术方案（如有）、代码或文档变更、验证记录、报告。

## 验证

跑与改动相关的测试或站点构建，并写下命令和结果。本产品的公开站任务按已确认方案做定向验证，不默认全量 `npm test`。

## 完成条件

已确认范围逐项落地，关联消费者已同步，验证按约定跑完，命令和退出码可查，剩余风险与回滚写进报告。

## 示例请求

```text
按已确认的公开站技术方案，先写生成器和页数合同，再加概念页和工作流页。
```
