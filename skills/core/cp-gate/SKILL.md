## CP 定义

| CP | 名称 | dev | fix | 目的 |
|:--:|------|:---:|:---:|------|
| CP1 | 需求/问题确认 | 🔴 必须 | 🔴 必须 | 确认 AI 理解与用户一致 |
| CP2 | 方案确认 | 🔴 必须 | 🔴 必须 | 确认技术方案可行后再编码 |
| CP3 | 交付/执行确认 | 🔴 必须 | 条件触发 | 确认实施计划后开始逐文件执行 |

### CP3 触发条件

| 工作流 | 条件 |
|--------|------|
| dev | 始终必须 |
| fix | ≥5 文件变更 **或** 含高风险操作 |
| fix | 其他场景 → 可选 |

**高风险操作**：DDL 变更 / 配置文件变更（.env/package.json/CI） / 文件删除 / 直接影响生产环境的修改

## 执行规则（C02 约束）

1. **严格按序**：CP1 → CP2 → CP3，不得跳过中间步骤
2. **禁止合并**：不得将 CP1+CP2 合并为一次输出
3. **每个 CP 独立确认**：输出后必须等待用户明确响应
4. **用户请求 ≠ CP 确认**：用户说"帮我做X"不等于 CP1 已通过
5. **"继续" ≠ CP3 授权**：必须先展示变更计划才能进入执行
6. **跨轮次状态保持**：CP 确认状态不因后续轮次消息重置
7. **产物文件前置创建**：输出 CP 确认请求前，对应产物文件必须已写入磁盘（CP1 → `01-需求概述.md`；CP2 → `02-技术方案.md`）

## CP 响应处理

| 用户响应 | 处理方式 |
|---------|---------|
| ✅ 确认（"可以"/"没问题"/"确认"） | 进入下一阶段 |
| ✏️ 修正（"X 部分改为 Y"） | 应用修正后重新输出当前 CP，等待再次确认 |
| ❌ 拒绝（"不对"/"重来"） | 回退到当前 CP 重新分析 |
| ？追问 | 回答后重新输出当前 CP，等待确认 |
| 🔀 模糊（含批评/情绪/意图不明）| **不得推进**，必须明确询问再等待显式响应 |

## CP 记录格式

报告中「CP 确认记录」表：

```markdown
| CP | 状态 | 用户响应 | 时间 |
|:--:|:----:|---------|------|
| CP1 | ✅ | 确认需求理解正确 | HH:MM |
| CP2 | ✏️→✅ | 修正后确认方案 | HH:MM |
| CP3 | ✅ | 确认实施计划 | HH:MM |
```
