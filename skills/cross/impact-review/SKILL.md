# Impact Review Skill

## 职责

在 dev/fix 工作流执行完成后，评估代码变更的潜在影响范围，输出影响评估报告。

## 触发时机

| 工作流 | 触发条件 |
|--------|---------|
| dev | 涉及接口变更/新模块/架构调整 |
| fix | 修复影响核心功能或多个模块 |
| dev-refactor | 始终触发（Breaking Change 风险） |

**豁免**：`dev-docs`、`dev-plan-review`、`analyze`、`audit`、`chat`

## 六维评估框架

| 维度 | 内容 |
|------|------|
| 1 受影响功能 | 本次变更直接修改的功能列表 |
| 2 直接依赖 | 直接调用/引用被修改模块的代码 |
| 3 间接影响路径 | 通过依赖链间接受影响的模块 |
| 4 用户可见行为变化 | 用户/调用方感知到的行为差异 |
| 5 回归风险评级 | 🔴 高 / 🟡 中 / 💡 低（基于影响范围） |
| 6 验证策略 | 需要额外验证的测试点和验证方法 |

## 输出格式

```markdown
## 影响评估报告

**变更摘要**：[一句话描述本次变更]
**回归风险**：🔴 高 / 🟡 中 / 💡 低

| 维度 | 内容 |
|------|------|
| 受影响功能 | ... |
| 直接依赖 | ... |
| 间接影响 | ... |
| 用户可见变化 | ... |
| 验证策略 | ... |
```

## 关键规则

- 🔴 高风险变更**必须**补充回归测试用例
- 影响范围 >3 个模块时，建议分批发布
- Breaking Changes 必须在评估中标注并提供迁移指南
