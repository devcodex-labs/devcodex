# 需求管理

> AI 在新建需求或更新需求状态时，严格按本页规范执行。需求目录以当前活跃版本为准，当前为 `website/docs/versions/v1/1.0.1/requirements/`。active-root CP1 先判定入口类型：无产品角色的纯新需求走 `00-需求概况.md` → `01-需求确认.md`；有产品角色直接提供完整需求走 `01-产品需求.md` → AI / 研发缺口 / 冲突检查 → `02-技术方案.md`；需求变更走 `00-需求变更概况.md` → `01-需求变更确认.md`，并回写目标需求真相源；Bug 问题走 `bugs/<问题>/00-问题概况.md` → `01-问题确认.md` 并进入 fix。确认后再进入 `02-技术方案.md` → `04-实施计划.md` → `05-实施进度.md` → `06-关键决策.md`。产品输入型需求以双方确认后的业务事实源或产品直接提供的完整需求为准：需求方和产品不填写验收标准、测试用例、数据库字段或接口 Schema；实现验收由技术方案、实施计划和测试方案从产品原文派生。产品完整需求模板正文只给产品填写完整 PRD，AI / 研发缺口检查记录在 CP1 摘要、`02-技术方案.md` 或报告中，不放入产品填写模板正文。

---

## 优先级判断

| 优先级 | 判断标准 | 目录 |
|--------|---------|------|
| **P0** | 项目基础骨架，其他一切的前提（根目录、profile、文档站）| `requirements/p0/` |
| **P1** | 所有功能需求共用的横切规范，必须在 P2 之前定义和实施 | `requirements/p1/` |
| **P2** | 具体功能模块（agents/skills/instructions 等）| `requirements/p2/` |

---

## 新建需求

### 需求方输入与产品需求确认

CP1 需求确认前必须先区分四类入口，不得把需求方输入、产品完整需求、需求变更和 Bug 问题混写：

| 模板 / 文件 | 填写 / 生成方 | 用途 | 不要求填写 |
|-----------|---------------|------|------------|
| `00-需求概况.md` / 纯新需求概况模板 | 业务、运营、客户、老板、内部使用方等需求提出者 | 用口语化问题表达新增能力、页面、流程或业务规则的原始诉求：希望系统做到什么、现在怎么凑合处理、必须遵守的业务口径、希望出现 / 不能接受的例子、截图表格链接和不确定点 | 完整 PRD、验收标准、测试用例、数据库字段、接口 Schema |
| `01-产品需求.md` / 产品完整需求模板 | 公司产品经理 / 产品负责人 | 当公司已有产品角色时，由产品直接提供完整 PRD：业务目标、范围边界、Mermaid 主流程图、文字步骤图、节点解释、页面交互、字段描述、业务规则、示例 / 反例和待确认问题 | AI 生成 / 重写的产品需求草稿、AI / 研发缺口检查表、验收标准、测试用例、数据库字段、接口 Schema、技术方案 |
| `00-需求变更概况.md` / 需求变更概况模板 | 需求提出者或产品 | 描述已确认需求的原需求基线、变更前后差异、影响范围、不变内容和目标真相源 | 把变更当成纯新需求、根因分析、技术方案、测试用例 |
| `01-需求确认.md` / `01-需求变更确认.md` / 产品需求确认模板 | AI 根据输入生成草稿，产品补充归一化，需求方 + 产品确认 | 沉淀双方确认后的业务事实源，供研发和 AI 稳定执行；变更确认后必须回写目标需求真相源 | 技术实现、数据库字段、接口 Schema、测试用例 |
| `bugs/<问题>/00-问题概况.md` / `01-问题确认.md` | 报告方输入，AI / 研发确认 | 表达 Bug 现象、重现步骤、期望行为、实际行为、环境版本、频率、影响范围和证据，并进入 fix 工作流 | 产品新需求、需求变更、修复方案、测试用例 |

AI 生成产品需求草稿时，必须保留需求方原始输入锚点、直接提取内容、合理推导内容、冲突 / 遗漏和待确认问题。产品直接提供 `01-产品需求.md` 时，AI / 研发只做缺口 / 冲突检查和澄清，不生成或重写产品需求；缺口检查记录在 CP1 摘要、`02-技术方案.md` 或报告中，确认后直接进入技术方案。`00-需求概况.md`、`01-产品需求.md`、`00-需求变更概况.md`、`00-问题概况.md` 与确认文档不得混写；只有事实源确认后，才进入技术方案。

需求涉及新增或改变 Rule/Skill、Prompt、MCP Resource/Resource Template/Tool、Task 增强 Tool、CLI 或 Hook 时，CP1 只确认目标、消费者、控制方、权限和兼容边界；CP2 必须引用中央 `CapabilitySurfaceDecisionV1`。产品需求不得直接把“新建 Skill/MCP”写成既定实现。具体选择标准见 [MCP 能力边界与载体决策](/specs/mcp-capability-boundary)。

`00-需求概况.md` 必须让非产品 / 非研发需求方一眼知道怎么填：每个抽象字段都要配“这项填什么、可以怎么写、可以不填的情况、不要写什么”。需求方可以直接写“没有 / 不知道 / 暂无 / 需要产品帮忙整理”，AI / 产品不得把这些空白或不确定内容静默补成已确认事实。

### P0 / P2（单文件）

在对应目录下创建 `<需求名>.md`，填写以下结构：

```markdown
# 需求：<名称>

**状态**：⬜ 待开发
**优先级**：P0 / P2

## 目标
## 已完成产物（完成后填写）
## 约束
```

### P1（目录 + 5 文件）

```
requirements/p1/<需求名>/
├── index.md       ← 需求确认（版本正式信源）
├── design.md      ← 技术方案（CP2 后填写）
├── plan.md        ← 实施计划（CP3 后填写）
├── progress.md    ← 实施进度（持续更新）
└── decisions.md   ← 关键决策（随时追加）
```

> `progress.md` / `05-实施进度.md` 不是所有小任务的默认文书；跨多轮/多阶段、阻塞、用户要求持续跟踪、多批次、预计修改 ≥10 文件、控制面任务、模板-示例-校验链或部署同步联动时必须创建并持续更新。

### 需求确认（index.md）必填结构

```markdown
# <需求名> — 需求确认

> **优先级**：P1 · **状态**：⬜ 待开发

## 需求背景      → 为什么要做，目标用户是谁，证据来源是什么
## 业务目标      → 期望业务结果与业务成功信号
## 需求定义      → 做什么（分条列出），含优先级和产品事实源
## 字段描述      → 业务含义、来源、展示、编辑规则；不定义数据库字段或接口 Schema
## 前端交互      → 页面入口、用户流、状态、反馈、输入方式、可访问性和设计来源
## 约束条件      → 不能踩的红线（⛔ 开头）、依赖、非功能业务约束
## 流程图        → Mermaid 主流程图 + 文字步骤图 + 节点解释
## 示例与异常    → 正例、反例、边界例、异常回退和待确认问题
## 派生边界      → 哪些内容由研发 / AI 在技术方案中派生验证
## 关联需求      → 与哪些需求有依赖关系（表格）
## 开发文档      → 链接到 design/plan/progress/decisions（表格）
## 版本变更记录  → 需求演进历史（表格，倒序）
```

## 更新需求状态

需求状态变更时，**同步更新以下两处**：

1. `index.md` 页眉：`⬜ 待开发` → `🔄 开发中` → `✅ 已完成`
2. `requirements/index.md` 总览表对应行状态列

---

## 需求变更处理

需求定义发生变更时：

1. 先创建或更新 active-root 的 `00-需求变更概况.md`，明确原需求基线、变更前后差异、影响范围、不变内容和目标真相源
2. 由 AI / 产品生成 `01-需求变更确认.md`，完成需求方 + 产品双方确认
3. 回写 `index.md` 或目标 `01-需求确认.md` 的对应内容，并在 `版本变更记录` 追加一行
4. 在 `decisions.md` 追加决策记录（如涉及架构决策）
5. 在 `versions/v1/<active-version>/CHANGELOG.md` 追加变更日志行（当前为 `versions/v1/1.0.1/CHANGELOG.md`）

## 更新 sidebar

新增需求文件后，在 `website/rspress.config.ts` 的 `sidebar['/versions/']` 对应分组中加入链接。

> ⛔ AI 每次新建需求文件后，必须同步更新 sidebar，否则页面不可访问。
