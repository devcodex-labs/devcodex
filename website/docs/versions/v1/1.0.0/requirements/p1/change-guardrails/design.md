## 方案概述

本方案不新增工作流，而是在现有 `intent → load-profile → common/dev/fix/analyze` 规则链路中补三类护栏：

1. **任务切换护栏**：当会话可能切到新需求时，先用“意图优先、关键词兜底”的顺序判断是否需要提醒用户当前存在未提交变更。
2. **提交摘要护栏**：当用户明确要求提交时，约束 commit subject 必须是一句简洁、聚焦主变更的描述。
3. **事实源护栏**：当任务正在判断外部平台 / 框架 / API / 兼容性 / 第三方工具语义时，优先读取官方文档，再做分析或实施。

## 核心设计

### 1. 任务切换护栏

在 `instructions/01-common.instructions.md` 增加一条跨工作流规则：

- **第一步：判断是否属于新需求切换**
  - 优先根据当前会话上下文、已完成任务、用户目标变化做意图判断。
  - 仅当上下文不足以稳定判断时，才允许以关键词、措辞变化、主题漂移作为降级信号。
- **第二步：判断是否存在未提交变更**
  - 若工作区干净，则无需额外提醒，继续按正常流程推进。
  - 若工作区不干净，则输出边界提醒，而不是直接阻断。
- **第三步：提醒用户确认边界**
  - 先提交当前变更后切换；
  - 明确继续并行处理；
  - 明确说明仍属同一需求。

#### 设计原则

- 以“减少混做”而不是“强制中断”为目的。
- 仅在“新需求切换 + 工作区有未提交变更”两个条件同时满足时触发。
- 不与安全底线 S01/C10 混淆，不升级为阻断级规则。

### 2. Commit Subject 简洁化护栏

在 `instructions/01-common.instructions.md` 与 `10-dev` / `11-fix` 中补一条提交输出规则：

- 用户明确要求 `commit` 时，Agent 输出的 commit subject 必须为一句简洁短语。
- 主题应只描述“本次主变更是什么”。
- 以下内容禁止塞进 subject：
  - 大段背景说明
  - 验证步骤罗列
  - 风险/回归测试/多项并列总结
- 若需要补充上下文，应写在：
  - 回复正文
  - 报告文件
  - commit body（若用户显式要求）

#### 示例约束

| 场景 | 推荐 | 不推荐 |
|------|------|--------|
| 文档收口 | `docs: tighten task-switch guardrails` | 把整段需求摘要拼进 commit message |
| 规则修正 | `rules: prefer intent over keyword triggers` | `fix: updated many instructions and docs after analyzing...` |

### 3. 官方文档优先护栏

在 `instructions/13-analyze.instructions.md` 强化 `research` 流程，在 `01-common` / `10-dev` / `11-fix` 加条件触发说明：

- 当任务涉及以下问题时，先查官方文档或官方参考：
  - 平台能力判断
  - 框架 API / SDK 行为
  - 版本兼容性 / 弃用项 / Breaking Change
  - 第三方工具参数、命令语义、限制条件
- 若官方文档不存在，再降级到：
  - 官方源码 / 官方仓库说明
  - 项目内已确认文档
  - 社区资料
- 本地纯实现问题不触发。

#### 触发边界

| 任务类型 | 是否触发 | 原因 |
|---------|:--------:|------|
| 修改本仓库规则文案 | 否 | 事实源在本仓库 |
| 判断 Copilot / VS Code 是否支持某能力 | 是 | 依赖官方平台事实 |
| 判断 Node 某 API 的版本支持情况 | 是 | 依赖官方版本文档 |
| 修复已定位的本地逻辑 bug | 否 | 不属于外部事实判断 |

## 风险与约束

- 任务切换提醒如果写得过宽，会误伤同一需求的连续迭代，因此必须绑定“意图变化 + 工作区脏状态”双条件。
- 官方文档优先如果写成全局硬规则，会显著拖慢本地纯实现任务，因此必须是条件触发。
- commit 简洁化若扩展到 body 模板，会放大本次变更面，因此本方案只约束 subject。

## 验证方案

1. 构造“旧任务未提交 + 用户发起新需求”的对话样例，验证会先提醒边界。
2. 构造“同一需求继续微调”的对话样例，验证不会误报必须先提交。
3. 构造“用户要求 commit”的执行样例，验证输出 subject 只有一句简洁描述。
4. 构造“分析 VS Code / Copilot / Node 官方能力”的样例，验证先读官方文档。
5. 构造“本地纯规则修正”的样例，验证不会平白触发官方文档前置步骤。
