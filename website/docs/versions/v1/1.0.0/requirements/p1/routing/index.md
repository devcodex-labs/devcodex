# ⑦ 路由到工作流 — 需求概况

> ⚠️ 历史快照说明：本页保留 `1.0.0` 阶段的路由需求。当前版本 `token-check` 只是授权占位，不再把“授权门控后进入执行”作为当前行为描述。

> **优先级**：P1 · **状态**：✅ 已实现

---

## 需求背景

开发阶段合规检查通过后，需要将意图准确分流到对应的工作流。  
DevCodex 支持多种工作流（chat/resume/dev/fix/audit/analyze/self-fix/plan），每种的执行路径和约束完全不同，混淆路由会导致错误的流程执行。

---

## 需求定义

路由节点是主流程的**第七个阶段**，负责将意图映射到对应工作流：

| 路由分支 | 触发条件 | 处理方式 |
|---------|---------|---------|
| chat 快速路径 | 三问法全指向分析 + 无文件变更 | 跳过 CP 和报告，仅写记忆 |
| resume 恢复路径 | 记忆中存在 🔄 + 用户说"继续"/"恢复" | 读记忆 → 还原上下文 → 重路由 |
| 违规质疑路由 | 用户质疑规范违反 | 强制路由到 audit |
| 标准工作流 | dev/fix/audit/analyze/self-fix/plan | 当前全量开放，路由后进入执行 |
| 多意图处理 | ≥2 个意图 | 按序逐一路由，独立走完整工作流周期 |

---

## 约束条件

- 路由结果必须唯一（不能同时进入多个工作流）
- 多意图时必须串行处理，禁止并行（C07）
- resume 路径读取记忆后必须重新走完整路由判断

## 验收标准

- [ ] 所有意图类型都有对应的路由分支
- [ ] chat 路径正确豁免 CP 和报告
- [ ] resume 路径读取记忆后重新路由
- [ ] 多意图时串行处理，不并发
- [ ] 用户质疑违规时自动路由到 audit
