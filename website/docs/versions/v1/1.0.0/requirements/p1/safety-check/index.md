# ② 安全检查 — 需求概况

> **优先级**：P1 · **状态**：✅ 已实现

---

## 需求背景

预检查完成后，在进入摘要和记忆阶段之前，必须有一道强制闸门判断当前请求是否触碰安全底线。  
如果违规请求进入后续执行链，会导致敏感信息泄露、危险操作执行或规范被绕过，损失极难恢复。

---

## 需求定义

安全检查是主流程的**第二个必经阶段**，分三种判定结果：

| 判定结果 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 通过 | 无任何安全底线违规 | 继续主流程，进入写入摘要 |
| 操作级违规 | 触发 S01/S06 等可阻断违规 | 阻断该操作，给出合规替代，继续主流程 |
| 致命违规 | 触发 S02/S03 等致命违规 | 写入违规审计记录，立即终止请求处理 |

### 安全底线（S01~S06）

| 编号 | 规则 |
|------|------|
| S01 | 删除/破坏性操作需确认 |
| S02 | 禁止硬编码敏感信息 |
| S03 | 禁止编造规范内容 |
| S04 | 禁止 overwrite 源码/规范文件 |
| S05 | 记忆+报告自动写入 |
| S06 | 禁止执行危险命令 |

---

## 约束条件

- 安全检查**不可跳过**，包括全自动模式（S01~S06 全程强制）
- 致命违规（S02/S03）触发后**立即终止**，不进入后续节点
- 操作级违规（S01/S06）阻断后，必须给出合规替代方案后才能继续
- 违规审计记录写入 `data/violations.md`

- [ ] S01/S06 触发时给出合规替代后继续
- [ ] 全自动模式下安全底线不可被跳过
- [ ] 阻断并给出合规替代的子流程正确执行
