# 模板边界与开发流程收口 — 技术方案

> **需求来源**：[模板边界与开发流程收口 — 需求概况](./index)
> **状态**：🟡 待确认

---

## 方案概述

本方案的核心不是“再多写几条模板字段”，而是把 DevCodex 当前分散在 profile、versioned requirements、prompts、instructions、skills 里的同一组语义重新分层：

1. **正式需求层**：`website/docs/versions/v1/<active-version>/requirements/`，负责版本内的正式需求、设计、计划、进度与决策留痕。
2. **执行模板层**：`prompts/*.prompt.md`，负责约束 AI 在 CP1 / CP2 / CP3 生成怎样的产物结构。
3. **流程门禁层**：`instructions/10-dev.instructions.md`、`instructions/02-output-paths.instructions.md`、`skills/dev-plan-review/SKILL.md`，负责在开发流程中检查上述边界是否被遵守。

最终目标是让三层对同一件事使用统一语义：

- 需求回答“要实现什么、用户如何感知、结果如何验收”
- 方案回答“准备怎么实现、关键节点和公共契约是什么”
- 计划回答“按什么顺序做、做到哪一步、风险如何控制”

在模板策略上，本方案采用“**先结合、后统一**”而不是直接二选一：

- **项目当前需求模板**更适合作为正式 requirement 包的治理骨架，承载版本目录、影响范围、开发文档状态、版本变更记录等项目特有治理信息。
- **新调整的通用 requirement prompt**更适合作为 CP1 的内容采集骨架，承载目标、业务流程、节点说明、功能需求、非功能需求、验收标准等通用内容结构。
- 第一阶段，两者结合后，项目模板负责“正式留痕与治理”，通用模板负责“表达质量与采集完整度”。
- 第二阶段，以当前项目验证出的映射关系为依据，回抽出一个**统一通用模板**：保留通用核心骨架，并提供项目级扩展位与覆盖点，避免长期维持两套同义模板。

## 现状分析

### 1. 当前结构事实

| 位置 | 当前事实 | 问题 |
|------|---------|------|
| `.devcodex/profile/01-项目信息.md` | 正式需求入口已冻结到 `website/docs/versions/v1/<active-version>/requirements/` | 与 prompt 的挂载面未显式对齐 |
| `prompts/requirement.prompt.md` | 仍声明应用于 `.devcodex/**/requirements/**` | 若未显式写清“默认模板 vs 项目自定义优先”关系，容易让首次接手者误读当前项目正式需求入口 |
| `prompts/technical-design.prompt.md` | 已有接口设计，但“实现流程 / 节点职责”还不是主结构 | CP2 容易继续偏模块说明式 |
| `instructions/02-output-paths.instructions.md` | `03` 条件、`04` 强制、`05` 条件 | 只定义了触发，不足以解释职责分工 |
| `instructions/10-dev.instructions.md` | CP1 → CP2 → CP3 结构完整 | 但三阶段关注点未与模板语义完全对齐 |
| `skills/api-verification/SKILL.md` | 执行前提是“读取接口定义” | 反证公共契约应在 EXEC 前完成设计 |

### 2. 根因定位

根因不是单个模板缺字段，而是**同一语义被四处表述但没有唯一边界**：

- 正式需求入口说一套
- prompt 模板的落点说一套
- 开发流程的 CP 关注点又说一套
- 实施类产物的职责与条件矩阵没有在一处统一解释

因此当前问题表现为：

1. 写需求时不确定是先写正式 versioned requirements，还是先落 `.devcodex` 模板。
2. CP1 和 CP2 都在“画流程图”，但没人明确两张图分别看什么。
3. `04-实施计划.md` 被视为固定成本，`05-实施进度.md` 又缺少依赖前提，导致实施产物关系松散。
4. 接口契约虽然在方案模板中已有入口，但没有被提升为 CP2 的硬前置，容易在 EXEC 阶段漂移。

## 核心设计

### 1. 正式需求层与执行模板层解耦

#### 设计

- 正式需求层继续以 `website/docs/versions/v1/<active-version>/requirements/` 为唯一信源。
- 执行模板层不再争夺“正式需求入口”语义，而是改为描述“当 AI 生成需求 / 方案 / 计划产物时，结构应是什么”。
- README、RULES、Profile 必须同步说明两层关系，避免再次出现“哪边才是主入口”的歧义。

#### 结果

- 项目自身开发按 versioned requirements 留痕。
- prompts 保留为通用默认执行模板，但要通过 profile / README / RULES 明确说明：当前仓库的正式需求仍写在 versioned requirements，项目自定义规则优先。
- 当前项目 requirement 文档继续保留现有 `需求背景 / 需求定义 / 约束条件 / 非需求 / 验收标准 / 影响范围 / 开发文档 / 版本变更记录` 的治理骨架；通用 requirement prompt 中更强的“目标 / 业务流程 / 节点说明 / 功能需求 / 验收表”结构，则以映射或嵌入方式注入到 `需求定义` 和 `验收标准` 的写法中，而不是整体替换项目模板。

#### 哪个更好

| 方案 | 优点 | 缺点 | 适用性判断 |
|------|------|------|-----------|
| 只保留当前项目模板 | 更贴合当前仓库的版本治理、需求包结构和变更留痕 | 对“用户结果 / 业务流程 / 节点说明 / 验收采集”的结构约束偏弱 | 不足，容易继续保持治理强、表达弱 |
| 只保留新调整的通用模板 | 对 CP1 内容采集更完整，业务表达更强 | 缺少当前项目 requirement 包的版本治理、影响范围、开发文档状态等项目特有骨架 | 不足，容易丢掉项目正式治理信息 |
| 两者结合（过渡路径） | 同时保留项目治理能力和通用表达能力，适合当前项目验证映射规则 | 仍然存在双层维护成本，不适合长期停留 | 当前阶段最合适 |
| 最终统一通用模板 | 一套模板即可覆盖通用核心语义，并通过扩展位承载项目差异 | 如果没有先做当前项目验证，容易抽象过度或丢失治理信息 | 作为目标形态最合适 |

结论：对 DevCodex 当前项目，**当前阶段先结合更合适，最终形态应收敛为一个统一通用模板**。

#### 最终统一模板的目标结构

统一通用模板建议拆成两层而不是一个纯扁平大表：

| 层次 | 职责 |
|------|------|
| 通用核心骨架 | 目标、业务流程、节点说明、功能需求、非功能需求、排除范围、依赖约束、验收标准 |
| 项目扩展位 | 版本治理、影响范围、开发文档状态、版本变更记录、项目专属兼容或发布字段 |

这样最终虽然是“一个通用模板”，但结构上仍允许项目通过扩展位最小化定制，而不必回退到完全分裂的两套模板。

### 2. 需求模板改造：业务结果优先

#### 设计目标

需求模板只回答以下问题：

1. 这个需求最终要让谁获得什么结果。
2. 用户如何触发、系统如何响应、在哪些条件下成功或失败。
3. 如何验证需求已经实现。

#### 模板改造点

| 模块 | 改造点 |
|------|--------|
| `§2 目标` | 强化“用户/系统能够……从而获得……”的结果表达 |
| `§3 业务流程` | 改写说明，明确这是业务/交互流程，而不是技术调用图 |
| `§3.2 节点详解` | 字段改成“谁触发、系统做什么、用户看到什么、成功/失败出口” |
| `§4 功能需求` / `§8 验收标准` | 明确每个核心需求必须能映射到至少一条独立验收用例 |

#### 复杂度策略

- 对有用户交互、分支判断、多轮实现的需求，流程图必填。
- 对极小型需求允许轻量化节点说明，但不得省略目标、范围、验收标准。

### 3. 技术方案改造：实现流程与公共契约前置冻结

#### 设计目标

技术方案要成为 CP2 的核心载体，而不是补充说明文档。

#### 模板改造点

| 模块 | 改造点 |
|------|--------|
| `§0 现状分析` | 增加“已有契约/已有结构基线读取”要求 |
| `§2.2 接口设计` | 提升为公共契约主入口，覆盖现状契约 → 目标契约差异与向后兼容口径 |
| `§2.3` | 从“数据流”升级为“实现流程 / 时序图 / 关键节点”主结构 |
| 新增节点说明区 | 逐节点说明责任模块、输入、输出、状态变化、失败处理 |
| 新增兼容性策略区 | 说明调用方兼容、文档迁移兼容、版本/宿主兼容与 Breaking Changes 的迁移方式 |
| 新增边界问题清单 | 说明哪些场景走轻计划、哪些场景必须冻结公共契约，以及异常/空值/宿主差异等边界 |
| `§8 实施约束` | 明确接口先后、Schema 先后、i18n 先后等技术顺序约束 |

#### 公共契约冻结规则

以下对象在 CP2 前必须确认：

- 对外 HTTP API
- RPC / CLI / Hook 入口
- Webhook / 消息事件
- Schema / Model / 类型定义
- 错误码与权限结果
- 关键返回字段与兼容性边界

若改造对象已存在，必须先读取现状定义，再输出差异表；若对象为新增，则必须与同类接口风格对齐。

#### 兼容性策略

技术方案中需要单独回答以下兼容问题：

| 兼容维度 | 需要说明的内容 |
|------|----------------|
| 调用方兼容 | 现有调用方是否可无感继续使用；若不行，迁移路径是什么 |
| 文档兼容 | 旧的 `.devcodex` 执行模板口径如何迁移到 versioned requirements 正式口径 |
| 版本兼容 | `1.0.0` 基线快照、`1.0.1` 活动版本与后续增量目录如何避免再次分裂 |
| 宿主/模式兼容 | 规则改造后，哪些语义适用于通用模板，哪些只适用于当前仓库正式需求体系 |

兼容问题不能只在 `§3 Breaking Changes` 或 `§9 风险与缓解` 中被动出现，而应作为方案设计时的显式输入。

#### 边界问题清单

技术方案中需要显式处理以下边界判断：

| 边界场景 | 需要说明的口径 |
|------|----------------|
| 极小型任务 | 是否允许只走轻计划摘要，不建完整 `04-实施计划.md` |
| 纯内部实现 | 是否可以不触发公共契约冻结，只保留模块边界和测试策略 |
| 公共接口变更 | 哪些字段/行为必须保证向后兼容，哪些变化属于 Breaking Change |
| 异常与缺省输入 | 空值、缺字段、未知类型、无匹配宿主能力时如何降级 |
| 跨轮次实施 | 何时必须进入 `05-实施进度.md`，何时不需要 |

边界问题不应只在执行阶段靠临场判断补充，而应在 CP2 阶段先冻结判断标准。

### 4. 实施类产物重构为职责矩阵

#### 设计目标

不是删除 CP3，而是让 `03/04/05` 三类产物各自解决不同问题。

#### 职责矩阵

| 产物 | 角色 | 触发条件 |
|------|------|---------|
| `03-实施方案/` | 复杂任务的结构拆分 | 多子模块 / 多阶段 / 跨服务 |
| `04-实施计划.md` 轻计划摘要 | 小到中型任务的实施顺序、依赖、完成标准 | 默认路径 |
| `04-实施计划.md` 完整计划 | 里程碑、回滚、风险、依赖全量展开 | 高风险 / 多模块 / 接口或 Schema 变更 / 跨轮次 |
| `05-实施进度.md` | 跨轮次跟踪状态 | 跨 2 轮以上会话或存在多里程碑，且已存在 `04` |

#### 实现要点

- `instructions/02-output-paths.instructions.md` 负责写清角色与触发条件。
- `implementation-plan.prompt.md` 负责体现轻计划和完整计划两档结构。
- `implementation-progress.prompt.md` 负责依赖 `04` 的状态同步，而不是独立存在。

### 5. 开发流程门禁与模板职责对齐

#### CP1

- 确认需求目标、业务流程、范围边界、验收标准。
- 不讨论实现节点细节，不在 CP1 引入技术时序图。

#### CP2

- 确认实现流程、节点职责、公共契约、兼容性策略、边界问题清单、Breaking Changes、测试策略。
- `dev-plan-review` 必须增加接口基线读取与公共契约冻结检查。
- `dev-plan-review` 还需要增加兼容矩阵与边界场景是否被显式说明的检查。

#### CP3

- 只确认实施顺序、里程碑、风险与回滚。
- 任务拆分必须从 CP2 已确认的节点/依赖反推，不得脱离方案重新定义主流程。

## 关键设计决策

| 决策 | 选择 | 原因 | 不选方案 |
|------|------|------|---------|
| 正式需求信源 | 继续使用 `website/docs/versions/v1/<active-version>/requirements/` | 已被 profile 冻结为当前项目事实入口；默认 prompt 模板不需要被删除，只需明确项目自定义优先 | 重新迁回 `.devcodex/requirements/` |
| requirement 模板策略 | 当前阶段“项目治理骨架 + 通用采集骨架结合”，最终阶段沉淀为统一通用模板 | 先验证映射，再抽象统一模板，风险最低 | 一开始就直接统一，或长期维持双轨 |
| 需求图语义 | 业务/交互/结果视角 | 贴近 CP1 需求确认目标 | 用技术流程图同时承担 CP1/CP2 |
| 技术图语义 | 实现流程/节点职责/公共契约 | 贴近 CP2 方案确认目标 | 继续仅以“模块划分 + 数据流”表达 |
| 接口契约时机 | CP2 前冻结 | `api-verification` 需要消费已确认定义 | EXEC 阶段边写边补 |
| 兼容性表达方式 | 作为技术方案显式结构单独说明 | 兼容问题是设计输入，不应只在风险阶段被动补充 | 仅在 Breaking Changes / 风险章节零散提及 |
| 边界问题表达方式 | 作为技术方案显式清单单独说明 | 边界判断直接影响 CP3 是否轻量、是否冻结契约、是否需要进度跟踪 | 留到执行阶段临场决定 |
| `04-实施计划.md` 策略 | 两档制：轻计划摘要 / 完整计划 | 减少小任务固定成本，同时保留高风险任务控制力 | 所有任务统一完整计划，或直接全条件化 |
| `05-实施进度.md` 策略 | 条件触发且依赖 `04` | 让进度跟踪建立在已确认计划上 | 无前提独立存在 |

## 风险与约束

- 若只改 prompt 不改 workflow/skill，CP1/CP2/CP3 的实际检查仍会沿用旧口径。
- 若只改 `02-output-paths` 不改 `implementation-plan/progress` 模板，产物解释仍会脱节。
- 若公共契约冻结规则写得过重，纯内部实现类需求可能被过度文书化，需要在规则中明确只约束公共边界。
- 若兼容性策略和边界问题仍只写在风险章节，执行时仍会回到“靠人脑补齐”的旧模式。
- 若 README / RULES 不同步，用户仍会从入口文档里读取到旧的语义边界。

## 验证方案

1. **文档边界验证**：Profile、README、RULES、版本化 requirements 对“正式需求入口”描述一致。
2. **需求模板验证**：当前项目 requirement 包骨架与 `requirement.prompt.md` 的分工清晰，且 `requirement.prompt.md` 样例能清晰表达业务流程与用户结果，而不是技术调用。
2.1 **统一模板目标验证**：方案中能明确说明从“两层结合”到“统一通用模板”的演进路径，以及统一模板的核心骨架和扩展位。
3. **技术方案验证**：`technical-design.prompt.md` 能体现实现流程、节点职责、公共契约冻结、兼容性策略与边界问题清单要求。
4. **流程门禁验证**：`10-dev.instructions.md` 与 `dev-plan-review` 能将 CP1/CP2/CP3 的检查重点与模板职责对齐。
5. **实施产物验证**：`03/04/05` 的角色与条件矩阵在 prompt 和 instruction 中一致，不再互相替代。
6. **样例回放验证**：选取一个“改已有公共接口”的需求，确认方案里能看到“现状契约 → 目标契约”差异表，以及兼容矩阵和边界问题处理口径。
