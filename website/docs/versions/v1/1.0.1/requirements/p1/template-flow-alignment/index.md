# 模板边界与开发流程收口 — 需求概况

> **优先级**：P1 · **状态**：🟡 待确认

---

## 需求背景

当前 `devcodex-v1.8.0` 已经具备较完整的需求模板、技术方案模板与开发流程规则，但在“正式需求体系”和“执行型模板体系”的边界上仍存在三类系统性漂移：

1. 项目 profile 已将正式需求入口冻结到 `website/docs/versions/v1/<active-version>/requirements/`，而 `prompts/requirement.prompt.md` 与 `prompts/technical-design.prompt.md` 仍只挂在 `.devcodex/**/requirements/**`。如果这两者的关系不被显式说明，新接手者或 AI 容易误读当前项目的正式需求入口；若将 prompts 明确定位为默认执行模板、项目自定义规则优先，则这本身不构成结构冲突。
2. 需求模板和技术方案模板都包含流程表达，但没有明确区分“需求图看最终功能/用户交互/业务结果”和“技术图看实现流程/节点职责/公共契约”，使 CP1 与 CP2 的确认重点容易重叠。
3. `03-实施方案/`、`04-实施计划.md`、`05-实施进度.md` 的职责与条件边界没有被统一描述，导致 CP3 固定成本偏高，小任务也容易被迫套完整文书。

如果不先把这三层关系收口，后续继续优化 prompt、instructions、skills 或 versioned requirements，只会把同一语义在不同位置重复维护，最终继续产生“看起来都对，但实际执行口径不一致”的问题。

---

## 需求定义

### NR-1：收口正式需求体系与执行型模板体系的边界

- DevCodex 必须明确：当前版本内的**正式需求信源**是 `website/docs/versions/v1/<active-version>/requirements/`。
- `.devcodex/**/requirements/**` 下的 prompt 模板继续保留，但要显式写清其定位是“默认执行模板契约与 AI 产物生成参考”；若项目已有自定义 requirement 规范，则以项目自定义为准，避免被误读为当前项目的正式需求入口。
- Profile、README、RULES、版本化需求文档之间必须能一致回答“正式需求写在哪里、执行模板服务什么阶段”。
- 对当前 DevCodex 项目，不采用“项目模板”或“通用模板”单独替代对方的路线，而采用**两层结合**：项目版本化需求模板负责正式治理骨架，通用 requirement prompt 负责 CP1 的业务结果、流程图、节点说明、功能需求与验收采集骨架。
- 上述“两层结合”不是最终长期形态；本需求的目标是经过当前项目验证后，**沉淀出一个统一的通用 requirement 模板**。该模板应保留通用核心骨架，并提供项目级扩展位，而不是继续长期维护两套彼此平行的需求模板。

### NR-2：需求模板必须表达“做什么”和“最终结果”，而不是实现细节

- 需求模板应以最终功能、用户交互、业务结果、验收标准为主语义。
- 需求流程图必须表达用户/系统视角下的业务流转，不应退化为技术调用图。
- 节点说明应重点回答：谁触发、系统做什么、用户看到什么、在哪种条件下结束，而不是写模块内实现细节。
- 对纯极小型改动可允许轻量表达，但不得删掉“最终结果”和“验收标准”的需求骨架。

### NR-3：技术方案模板必须表达“怎么实现”，并在 CP2 前冻结公共契约

- 技术方案必须以实现流程、节点职责、模块边界、数据流和异常处理为主结构。
- 对外 HTTP API、RPC、Webhook、消息事件、Schema/Model、错误码、权限结果、关键返回字段等**公共契约**，必须在 CP2 阶段设计并确认，不得把 EXEC 阶段或 `api-verification` 反向当作设计来源。
- 若修改已有公共接口，必须先读取现状接口/类型/示例，再输出“现状契约 → 目标契约”的差异说明。
- 技术方案必须显式给出**兼容性策略**，至少覆盖：现有调用方兼容、历史文档/旧模板兼容、版本化 requirements 与 `.devcodex` 执行模板之间的迁移兼容，以及 Breaking Changes 的降级或迁移路径。
- 技术方案必须显式给出**边界问题清单**，至少覆盖：极小型任务是否走轻计划、纯内部实现是否免公共契约冻结、公共接口变更的兼容边界、空值/缺字段/未知宿主能力/跨轮次实施等异常与边界场景。
- 技术方案图与节点说明必须服务“准备怎么实现”，不能与需求图重复表达用户结果。

### NR-4：实施类产物必须重新定义职责与条件矩阵

- `03-实施方案/` 负责复杂任务的分块实施落点，仅在多子模块、多阶段或跨服务需求时创建。
- `04-实施计划.md` 不应简单地在所有任务上强制使用同一重量级模板，而应支持“轻计划摘要 / 完整实施计划”两档。
- `05-实施进度.md` 继续保持条件触发，仅在任务跨 2 轮以上会话、或存在多个里程碑/阶段执行时创建；且必须依赖已存在的 `04-实施计划.md`。
- CP3 应基于已确认的技术方案节点与依赖顺序反推任务，而不是脱离方案重新平铺拆任务。

### NR-5：开发流程的 CP1 / CP2 / CP3 关注点必须同步调整

- CP1 重点确认：需求目标、用户交互、业务流程、验收结果、范围边界。
- CP2 重点确认：实现流程、节点职责、公共契约、Breaking Changes、测试策略。
- CP3 重点确认：实施顺序、里程碑、风险与回滚，而不是重复定义需求或技术方案。
- `dev-plan-review` 与相关 instructions 必须使用同一口径校验上述三层职责，避免检查项继续交叉污染。

### NR-6：相关入口文档必须同步解释新边界

- README、RULES、Profile、版本化 requirements 总览必须同步说明：
  - 正式需求的落点
  - prompt 模板的职责
  - 需求图与技术图的语义边界
  - `03/04/05` 三类实施产物的职责差异

---

## 约束条件

- 不新增新的工作流类型，继续复用现有 `dev.default` 主路径。
- 不通过删除流程图或删减文档骨架来“减负”，减负应通过明确条件化与降低图粒度实现。
- 不把当前项目重新迁回 `.devcodex/requirements/` 作为正式需求入口。
- 不把接口契约设计延后到 EXEC 阶段处理。
- 不在本需求中顺带扩展无关工作流或宿主能力。

---

## 非需求（明确排除）

| 排除项 | 理由 |
|------|------|
| 一次性重写全部 prompts / instructions / skills | 本需求先收口边界与职责，不追求首轮全量重写 |
| 取消 CP3 | 问题在于职责与重量级定义不清，不是 CP3 本身没有价值 |
| 让所有任务都必须产出完整 `plan/progress/decisions` 五件套 | 与小任务真实执行成本不匹配 |
| 将 `api-verification` 升级为接口设计器 | 它应消费已确认契约，而不是反向补设计 |

## 验收标准

| # | 标准 | 验证方式 |
|---|------|---------|
| AC-1 | 当前活动版本文档能够明确说明 `website/docs/versions/v1/<active-version>/requirements/` 才是正式需求入口 | 文档审查 |
| AC-2 | 需求模板说明能明确体现“最终功能 / 用户交互 / 业务结果”优先，而非实现细节 | Prompt 审查 |
| AC-2.1 | 当前项目的版本化需求模板与通用 requirement prompt 的分工能够被清楚解释，不再被误读为二选一关系 | 文档审查 |
| AC-2.2 | 能明确说明“两层结合”只是过渡验证路径，最终会收敛到一个统一通用模板，并保留项目扩展位 | 文档审查 |
| AC-3 | 技术方案模板说明能明确体现“实现流程 / 节点职责 / 公共契约前置冻结 / 兼容性策略 / 边界问题清单” | Prompt 审查 |
| AC-4 | `03/04/05` 的职责与条件矩阵能被规则和模板一致表达，不再互相替代 | Prompt + Instruction 交叉审查 |
| AC-5 | `dev.default` 的 CP1/CP2/CP3 关注点能与需求图 / 技术图 / 实施计划三层结构一致 | 工作流规则审查 |
| AC-6 | 对已有公共接口的改造方案中，能看到“现状契约 → 目标契约”差异说明 | 技术方案样例审查 |
| AC-7 | 技术方案样例中能看到明确的兼容矩阵与边界问题处理口径，而不是仅在风险章节一笔带过 | 技术方案样例审查 |

## 影响范围

### 预期变更模块

| 模块 | 变更方向 |
|------|---------|
| `prompts/requirement.prompt.md` | 强化需求图与节点说明的业务语义，明确 CP1 关注点 |
| `prompts/technical-design.prompt.md` | 强化实现流程、节点职责与公共契约前置冻结 |
| `prompts/implementation-plan.prompt.md` | 支持轻计划摘要 / 完整计划两档 |
| `prompts/implementation-progress.prompt.md` | 明确依赖 `04-实施计划.md` 的条件触发 |
| `instructions/02-output-paths.instructions.md` | 收口 `03/04/05` 的职责与触发条件 |
| `instructions/10-dev.instructions.md` | 收口 CP1 / CP2 / CP3 的确认重点 |
| `skills/dev-plan-review/SKILL.md` | 对齐接口基线读取、公共契约冻结与 CP2 检查重点 |
| `README.md` / `RULES.md` / `.devcodex/profile/01-项目信息.md` | 同步正式需求入口与模板职责说明 |

### 潜在影响点

- 会降低小任务被强制套用完整 CP3 文书的概率，但要求规则层更明确地区分任务复杂度。
- 会提升 CP1 / CP2 的边界清晰度，但需要同步调整现有 prompt 示例和检查项。
- 会提升接口变更类任务的前置设计成本，但减少编码阶段的契约漂移。
- 会提高方案阶段的兼容性思考成本，但能减少实施期才发现旧调用方、旧文档和边界场景未覆盖的问题。
